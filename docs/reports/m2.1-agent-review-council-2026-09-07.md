# M2.1 independent automated security-council report

**Date:** 2026-09-07  
**Initial reviewed commit:** `d7a282947112a76d8e003155f0d0d3e03f6a5235`  
**Target:** PR #4, M2.1 specification and ADR 0010  
**Reviewer type:** three isolated automated agents; no human or organizational independence claimed  
**Initial verdict:** unanimous REQUEST CHANGES

## Independent mandates

- cryptographic protocol: Ed25519 acceptance, signing domain, key identity, replay and revocation;
- authority threat model: trust roots, grant scope, role separation, confused deputy, stale lineage;
- implementability/conformance: exact wire shapes, stable failures, bounds, fixtures and Python/Rust
  determinism.

Reviewers were read-only and submitted findings independently. GitHub Copilot review was requested
as an optional fourth signal, but GitHub did not assign the reviewer; it is not counted.

## Positive properties retained

- signatures never imply authority by themselves;
- private keys remain outside canonical objects and the trusted verifier;
- detached signatures preserve target identity;
- grant intervals are half-open and the kernel reads no ambient clock;
- M1.1 bytes remain unchanged;
- domain-separated exact-digest signing and canonical base64url remain the foundation.

## Re-review

The first revised frozen commit, `46a584e`, was independently re-reviewed by all three original
mandates. Verdict remained unanimous REQUEST CHANGES. The reviewers found that identity was pinned
but the rest of the authority-bearing policy/state projection was still caller-controlled; they
also found missing trust-domain equality, a selector/API cycle, under-specified transition history,
ASCII/Unicode ambiguity, and incomplete stable-code precedence.

Revision 3 addressed those findings with a separately pinned complete authorization context, an
operator-owned historical key registry and `advance_anchor` transition, signature-domain equality,
pairwise role separation, a two-phase evaluated/attested proposal API, ASCII signing identifiers,
strict library APIs with bounded invalid-point vectors, and an exact parse/code order. A final
re-review of the next frozen commit is pending. Acceptance still requires no remaining P0/P1,
explicit disposition of P2, full repository verification, and an updated unanimous verdict before
PR #4 may merge. Its review then found four narrower blockers: revocation washout, duplicate
constitution policy sources, mixed-order Ed25519 acceptance differences, and incomplete later-stage
code precedence. Revision 4 makes revocations cumulative, makes the constitution the sole policy
source, requires prime-order subgroup validation before both maintained verification libraries,
and freezes every later predicate's priority. A further frozen-commit re-review remains required.

## Residual risk

Automated reviewers can share blind spots and cannot provide legal, organizational, or real-world
operator independence. Passing this gate authorizes a bounded implementation experiment, not a
production security claim. M2.1 remains disabled by default and cannot append durable lineage.
