# M1.1 — Cross-language canonical decision envelope

**Status:** active
**Requirements:** REQ-CORE-003, REQ-AUTH-001, REQ-EVID-001, REQ-PROM-001,
REQ-LINE-001, REQ-REP-001
**Trust boundary:** Python evaluation plane → Rust trusted kernel → durable lineage
**Authority impact:** none; this increment represents authority facts but grants no authority

## Problem

Python and Rust currently express similar promotion concepts with different field names, money
types, reason text, ordering, and decision shapes. A signature added on top of that ambiguity
would authenticate implementation-specific bytes instead of one protocol object.

## Scope

- define protocol-safe candidate, evidence, context, decision, and decision-envelope shapes;
- represent cost as non-negative integer micro-US dollars;
- define deterministic reason codes and ordering;
- define a deliberately restricted canonical JSON profile;
- publish shared positive and negative fixtures;
- require Python and Rust to emit identical canonical bytes and SHA-256 envelope digests.

## Non-goals

- signatures, keys, or trust-chain validation;
- full RFC 8785 number canonicalization;
- SQLite persistence;
- network transport or schema negotiation;
- changing who is authorized to promote.

## Normative canonical JSON profile

The v1 signed surface permits JSON objects, arrays, strings, booleans, null, and integers in the
inclusive range `[-(2^53)+1, (2^53)-1]`. Floating-point values are forbidden. This avoids
cross-runtime ambiguity before a full standards review.

Canonical bytes are UTF-8 JSON with:

- object keys sorted by Unicode code point;
- no byte-order mark and no alternate UTF-16/UTF-32 wire encoding;
- duplicate object member names rejected at every depth;
- no insignificant whitespace;
- at most 64 object/array edges below the root value;
- arrays preserved in protocol-defined order;
- capability sets, evidence identifiers, and reason codes sorted lexicographically before
  serialization;
- capability names are non-empty and cannot contain commas because v1 parameterized reason codes
  use commas as an unambiguous separator;
- identifiers, check names, verifier names, capabilities, and reason parameters contain no ASCII
  C0 control character or DEL;
- non-ASCII characters emitted directly as UTF-8;
- only Unicode scalar values are accepted; lone surrogate code points are rejected;
- Unicode is not normalized, so canonically equivalent code-point sequences remain distinct;
- SHA-256 rendered as 64 lowercase hexadecimal characters.

Optional `candidate.metadata` and `evidence.details` are normalized to `{}` when omitted. Their
recursive values follow the same number, Unicode, duplicate-key, and depth rules. A schema match
is necessary but not sufficient: parsers also enforce lexical ordering of set-like arrays and
parameterized reason components that JSON Schema cannot express directly.

## Decision envelope

The decision first commits to a complete `promotion-input` envelope containing the candidate,
all evidence sorted by ID, trusted context, selected grant ID, exact constitution fields, and
`protocol_version`. Its canonical SHA-256 becomes `input_digest` in the decision. Consequently,
replacing evidence or policy under the same human-readable ID changes the decision identity.
The trusted context maps each parent lineage ID to its recorded capabilities. A candidate's
`baseline_capabilities` is only a declaration checked against that map; it is never an authority
source. A missing trusted baseline or a mismatch fails closed before any requested delta can be
granted.

```json
{
  "envelope_version": "variaxiom-envelope/v1",
  "kind": "promotion-decision",
  "payload": {
    "candidate_id": "candidate:1",
    "constitution_version": "constitution/v1",
    "evidence_ids": ["e:budget", "e:regression", "e:security", "e:unit"],
    "gate_version": "proof-gate/v1",
    "input_digest": "<lowercase SHA-256 of the promotion-input envelope>",
    "reasons": ["promotion.accepted"],
    "status": "accepted"
  }
}
```

Decision-envelope identity is `sha256(canonical_bytes(envelope))`. That digest is not embedded in
the hashed object. `input_digest` is embedded because it binds the decision to its complete replay
basis. Signatures are postponed to M2.1 and will sign a domain-separated digest.

## Stable reason codes

- `artifact.not_verified`
- `authority.baseline_mismatch`
- `authority.baseline_unknown`
- `authority.not_granted:<comma-separated sorted capabilities>`
- `candidate.cost_limit_exceeded`
- `evidence.artifact_mismatch:<evidence_id>`
- `evidence.failed:<evidence_id>:<status>`
- `evidence.missing_check:<check>`
- `evidence.self_verification:<evidence_id>`
- `evidence.verifier_diversity`
- `lineage.parent_unknown`
- `promotion.accepted`
- `rollback.target_unknown`

Reasons and evidence identifiers are deduplicated and sorted. An accepted decision contains only
`promotion.accepted`; a rejected decision never contains it.

## Fixture contract

Each `fixtures/conformance/v1/promotion/*.json` file contains:

- `case_id` and `protocol_version`;
- candidate, evidence, promotion context, and optional grant identifier;
- the complete expected decision;
- expected canonical decision-envelope JSON as a string;
- expected lowercase SHA-256 digest.

Unknown fields fail parsing. Fixture objects use the public schema names `candidate_id` and
`evidence_id` in both languages. Duplicate evidence IDs and malformed lowercase SHA-256 values
fail before policy evaluation. Candidate cost is a non-negative safe integer; a negative value is
structurally invalid rather than a policy rejection. The five security-invariant flags in
`constitution/v1` are fixed to `true` and cannot be disabled by input.

Wire input is UTF-8 JSON decoded by the strict parser before schema validation. JSON Schema alone
cannot distinguish integer-looking float lexemes such as `1.0`, express every lexical-order rule,
or bind trusted lineage authority; schema-only acceptance is therefore not protocol acceptance.

## Acceptance criteria

1. A bounded valid candidate is accepted identically in Python and Rust.
2. Ungranted authority is rejected identically.
3. An exact selected grant accepts its scope; a partial grant rejects only uncovered authority.
4. A candidate over the exact cost ceiling is rejected.
5. Evidence bound to another artifact cannot satisfy a mandatory check.
6. Self-verification plus failed evidence remains rejected with deterministic reasons.
7. Both implementations match every expected decision, canonical byte string, and digest.
8. Mutation of one envelope field changes the digest.
9. Floats and out-of-range integers are rejected by the canonicalizer.
10. CI runs conformance tests on Python 3.13/3.14 and Rust 1.98.1 across Linux, macOS, and Windows.
11. A candidate cannot hide newly requested authority by also claiming it as baseline authority.

## Rollback

The old Python `estimated_cost_usd` field is intentionally replaced before a public protocol
release. If cross-language consumers discover an incompatibility, retain fixtures and publish a
new envelope version; never silently reinterpret v1 bytes.
