# M2.1 — Identity, authority grants, and detached signatures

**Status:** accepted for disabled experimental implementation after unanimous automated council review
**Requirements:** REQ-CORE-003, REQ-AUTH-002, REQ-TRUST-001, REQ-EVID-001,
REQ-EVID-002, REQ-LINE-002, REQ-OPS-001, REQ-ID-001, REQ-SIG-001
**Trust boundary:** human-governed trust roots → signer/verifier boundary → deterministic promotion
kernel → durable lineage  
**Authority impact:** high; this increment authenticates authority facts but never derives authority
from a signature alone

## Problem

M1.1 gives Python and Rust identical canonical bytes and digests, but its identity names and
authority-grant map are unauthenticated bootstrap facts. Signing those facts without a precise
principal model, domain-separated message, expiry/revocation semantics, and trust-root input would
turn key possession into accidental authority and make replay difficult to distinguish from valid
reuse.

## Security invariants

1. A valid signature proves only that one key signed one message. It does not assign a principal,
   role, independence relationship, or authority.
2. Principal/key/role bindings and revocation state enter through an explicit trusted context; they
   are never accepted from candidate-controlled metadata.
3. Authority grants bind to the exact candidate-envelope digest and exact requested capability
   delta. A grant cannot authorize an adjacent candidate or a capability superset.
4. Verification uses an explicit evaluation time. The trusted kernel does not read the wall clock.
5. Candidate, evidence, grant, and decision signatures are detached. Existing canonical object
   identities do not change when an attestation is added.
6. Private key material never enters canonical protocol objects, repository fixtures, logs, model
   context, or the Rust kernel verifier.
7. Grant revocation and key revocation fail closed. Historical verification records the exact trust
   snapshot used; it never rewrites an earlier decision.
8. A proposer and verifier are independent only when their trusted principal identifiers differ.
   Different keys belonging to one principal do not establish independence.
9. An identity-context envelope is untrusted input until its digest, domain, sequence, and time
   exactly match a separately supplied operator-controlled authorization anchor.
10. A public key is bound to exactly one principal in a trust domain. Rebinding a key to another
    principal is forbidden in v1, including across snapshot history.
11. Signed evidence binds to the exact candidate-envelope digest, not to a reusable display ID or
    artifact digest alone.
12. Live authorization and historical replay are separate APIs. Replay can reproduce a result but
    can never authorize a lineage append or other side effect.
13. Every policy or state fact used by the gate is committed by a separately supplied trusted
    authorization anchor. Hashing caller-controlled state does not make that state trusted.

## Scope

- define v1 principal, public-key binding, trusted-identity-context, authority-grant, and detached-
  signature objects and schemas;
- introduce `candidate/v2` and `evidence/v2`; evidence commits to the exact candidate envelope;
- define canonical envelopes and SHA-256 identities for each new object;
- use Ed25519 signatures over a domain-separated message containing an exact envelope digest;
- use raw 32-byte Ed25519 public keys and raw 64-byte signatures encoded as unpadded base64url;
- derive every `key_id` from the raw public key;
- bind authority grants to an exact candidate digest, capability delta, issuer, validity interval,
  trust domain, constitution, capability vocabulary, audience, and non-delegable v1 policy;
- bind promotion to the exact canonical constitution envelope and its content-addressed artifact;
- introduce `promotion-input/v2` rather than reinterpret any M1.1 v1 bytes;
- publish shared positive, negative, replay, mutation, expiry, revocation, and cross-role fixtures;
- implement matching verification in Python and the small Rust trusted kernel.

## Non-goals

- certificate authorities, DID resolution, WebAuthn, OpenPGP, X.509, or network key discovery;
- threshold signatures, multisignatures, hardware-token integration, or automated key rotation;
- long-lived runtime capability leases or child-worker delegation;
- key generation or private-key custody inside the trusted kernel;
- signatures as proof of evaluator quality, human identity, or organizational independence;
- changing the M1.1 canonical JSON profile or silently upgrading `promotion-input/v1`;
- transactional SQLite persistence, transparency witnesses, remote timestamping, or authorization
  of a durable lineage append. Atomic head comparison and durable activation belong to M2.2.

## Normative encodings

The M1.1 canonical JSON profile remains normative. New binary fields use RFC 4648 base64url with
no `=` padding. Parsers decode and then re-encode to reject alternate spellings.

- Ed25519 public key: exactly 32 decoded bytes and 43 base64url characters.
- Ed25519 signature: exactly 64 decoded bytes and 86 base64url characters.
- `key_id`: `key:sha256:` followed by lowercase SHA-256 of
  `b"variaxiom-key/v1" || 0x00 || b"Ed25519" || 0x00 || raw_public_key_bytes`.
- envelope digest: 64 lowercase hexadecimal SHA-256 of canonical envelope bytes.
- time: non-negative Unix seconds in the M1.1 safe-integer range.
- interval: `not_before_unix_s <= evaluation_time_unix_s < expires_at_unix_s`.
- every validity interval is structurally valid only when `not_before_unix_s < expires_at_unix_s`.

The v1 algorithm identifier is the exact string `Ed25519`. Verification follows RFC 8032. Both
implementations must agree on every shared invalid-signature vector; permissive library defaults
cannot widen protocol acceptance. The selected trusted key binding and the detached signature must
both name exact `Ed25519`; either unsupported identifier returns
`signature.algorithm_unsupported` before decoding or equation verification.

## Resource and token bounds

All limits are checked before cryptographic work. Exceeding one returns
`input.limit_exceeded`. The limits are part of v1 and cannot be raised by an untrusted object:

- complete wire input: 1,048,576 UTF-8 bytes, checked before parsing or allocation; canonical
  nesting depth: 64, enforced while parsing;
- protocol token: 256 UTF-8 bytes and no C0, DEL, comma, or line-feed delimiters;
- principals: 64; keys per principal: 8; roles per principal: 8;
- revoked key IDs: 4,096; revoked grant IDs: 4,096;
- evidence envelopes: 256; capabilities per object: 128;
- detached signatures in one promotion input: at most 258 (candidate, 256 evidence, and one grant);
- metadata/details object: 65,536 canonical bytes;
- cryptographic verification operations: at most 259 per attested proposal, including selector.

Exact-limit and limit-plus-one fixtures are required for every collection family.

Capability identifiers are ASCII lowercase tokens in the versioned
`variaxiom-capability/v1` vocabulary. Allowed bytes are `a-z`, `0-9`, `.`, `-`, `/`, `:`, and `_`;
wildcards are forbidden. The broker/interpreter version is part of the namespace, so a semantic
change requires a new namespace and grants do not cross it. Case, Unicode lookalikes, whitespace,
implicit ports, or path normalization never create aliases.

Every identifier inserted into a signing message (`trust_domain_id`, `principal_id`, `key_id`,
`signed_kind`, and `signed_digest`) is an ASCII token of 1–256 bytes. Principal IDs match
`principal:[a-z0-9._:/-]+`; trust-domain IDs match `trust-domain:[a-z0-9._:/-]+`. Non-ASCII or an
empty suffix is structurally invalid rather than normalized.

## Principal and trusted key binding

A principal descriptor is a governance assertion, not a self-authenticating claim:

```json
{
  "principal_version": "principal/v1",
  "principal_id": "principal:verifier-a",
  "roles": ["evidence-verifier"],
  "keys": [
    {
      "key_binding_version": "key-binding/v1",
      "algorithm": "Ed25519",
      "key_id": "key:sha256:<64 lowercase hex>",
      "public_key_base64url": "<43 canonical characters>"
    }
  ]
}
```

A trusted identity-context payload has this exact shape:

```json
{
  "identity_context_version": "identity-context/v1",
  "trust_domain_id": "trust-domain:example",
  "snapshot_sequence": 7,
  "previous_snapshot_digest": "<64 lowercase hex or null for sequence zero>",
  "evaluation_time_unix_s": 1788739200,
  "principals": ["<complete principal descriptors>"],
  "revoked_key_ids": [],
  "revoked_grant_ids": []
}
```

`principal_id`, roles, and key bindings remain untrusted merely because they are present in this
payload. `evaluate_new` accepts them only after the complete identity-context envelope matches the
separate trusted authorization anchor defined below. A signature claiming a `principal_id` must
use a key bound to that principal in the anchored snapshot and the principal must have the role
required for the signed kind.

Required roles in v1 are:

| Signed kind | Required role |
|---|---|
| `candidate` | `candidate-proposer` |
| `evidence` | `evidence-verifier` |
| `authority-grant` | `authority-issuer` |
| `promotion-decision` | `promotion-selector` |

One principal may hold multiple roles in the context, but one promotion cannot count overlapping
roles as independent. The proposer, the set of evidence-verifier principals, the authority issuer,
and the promotion selector are pairwise disjoint. One verifier may sign multiple evidence items;
that principal counts once toward diversity. A violation returns `identity.role_conflict`.

Within one context, principal IDs are unique; roles and key bindings are non-empty, sorted, and
unique; key IDs and raw public keys are globally unique across all principals. The recomputed
`key_id` must match its binding. A key cannot move to another principal in a later v1 snapshot;
rotation adds a new key and revokes the old key. Ambiguity returns `identity.key_ambiguous`.

Principal descriptors are sorted by `principal_id`; roles by role; key bindings by `key_id`; both
revocation arrays are sorted and unique. Sequence zero requires `previous_snapshot_digest: null`;
later snapshots require the exact previous identity-context envelope digest.

### Trusted authorization context, anchor, and replay mode

Identity is only one part of authorization state. The gate also consumes a constitution, lineage,
parent authority, verified artifacts, and bounded policy values. These facts live in a complete
`authorization-context/v1` payload:

```json
{
  "authorization_context_version": "authorization-context/v1",
  "trust_domain_id": "trust-domain:example",
  "capability_namespace": "variaxiom-capability/v1",
  "lineage_id": "lineage:example",
  "constitution_envelope_digest": "<64 lowercase hex>",
  "constitution_artifact_hash": "<64 lowercase hex>",
  "known_lineage_ids": ["genome:parent"],
  "lineage_capabilities": {"genome:parent": []},
  "verified_artifact_hashes": ["<64 lowercase hex>"]
}
```

`known_lineage_ids` exactly equals the sorted keys of `lineage_capabilities`; all capability and
hash arrays are sorted and unique. The authorization-context envelope is a complete immutable
snapshot. None of its fields becomes trusted merely by appearing in a promotion input.

The verifier exposes distinct entry points:

```text
evaluate_new(untrusted_promotion_input, trusted_anchor) -> EvaluatedProposal
verify_attested_proposal(untrusted_attested_proposal, trusted_anchor) -> VerifiedProposal
replay_historical(recorded_attested_proposal, recorded_anchor) -> ReplayResult
initialize_anchor(genesis_identity_context, genesis_authorization_context,
                  trusted_now_unix_s) -> TrustedAnchor
advance_anchor(previous_anchor, previous_identity_context, next_identity_context,
               next_authorization_context, trusted_now_unix_s) -> TrustedAnchor
```

`trusted_anchor` is operator-controlled configuration, never read from a candidate, grant,
metadata, environment default, or embedded promotion input. It contains exactly:

```text
trust_domain_id
current_identity_context_digest
current_authorization_context_digest
current_snapshot_sequence
trusted_now_unix_s
key_ownership_registry
revoked_key_ids
revoked_grant_ids
```

`key_ownership_registry` is a sorted operator-controlled map from every key ID ever accepted in the
trust domain to its one principal ID, bounded to 4,096 entries. The two revocation fields are
sorted, monotonic sets, each bounded to 4,096 entries. All three are verifier state, not wire
input. `evaluate_new` requires exact equality between the anchor and both embedded context digests,
their trust domains, the identity sequence, and evaluation time before any key/role or policy
lookup. It then uses only the validated authorization-context snapshot for lineage, parent
capabilities, and verified artifacts, and only the pinned constitution for cost and verifier
threshold. Duplicate caller fields or alternate ambient defaults do not exist.

An older internally valid identity context fails with `identity.context_stale`; a self-minted or
swapped one fails with `identity.context_untrusted`; a self-minted or swapped authorization context
fails with `authorization.context_untrusted`. Every detached signature's `trust_domain_id` must
equal the anchor and both contexts before key lookup or cryptography, otherwise verification fails
with `signature.domain_mismatch`.

`initialize_anchor` is the only genesis path. It accepts explicitly operator-approved genesis
contexts, requires sequence zero and null previous digest, and seeds the permanent key-ownership
registry and both cumulative revocation sets from them. Its canonical input object is
`{initial_identity_context, initial_authorization_context, trusted_now_unix_s}` and is defined by
`schemas/v2/anchor-initialization.schema.json`. Initialization and advancement are trust-state
operations, not proposal authorization, and their conformance results set `authorizing: false`.

`advance_anchor` verifies both previous digests, requires the same domain, exactly the previous
sequence plus one, the exact `previous_snapshot_digest`, and non-decreasing trusted time. It rejects
any key whose historical registry owner changes, removal or reactivation of a revoked key or grant,
and any authorization context that is not separately approved by the operator. It unions the next
snapshot revocations into both permanent sets and adds new key ownerships to the registry. A
revoked key or content-addressed grant ID can never be reused; reauthorization requires a new key
or a new grant digest. The function returns the next immutable anchor; no implicit bootstrap exists.

`replay_historical` accepts only the anchor recorded with an existing event, reports
`authorizing: false`, and has no interface to append, activate, sign, or mutate lineage. It may
reproduce a past decision after later revocation without treating that decision as current.

## Signed target envelopes

M2.1 adds outer `variaxiom-envelope/v1` kinds `candidate`, `evidence`, `constitution`,
`identity-context`, `authorization-context`, `authority-grant`, `detached-signature`, and
`attested-proposal`. Their payloads retain an explicit object-level version.
`promotion-decision` remains the M1.1 envelope kind and payload.

`candidate/v2` contains the complete M1.1 candidate fields plus the required field
`candidate_version: "candidate/v2"`; no M1.1 bytes are reinterpreted. `evidence/v2` contains the
complete M1.1 evidence fields, replaces `subject_id` with required
`subject_candidate_digest`, and adds `evidence_version: "evidence/v2"`. The digest must equal the
exact canonical candidate-envelope digest. `evidence.verifier` and `candidate.proposer` must equal
the signing `principal_id`; a display label or model name cannot occupy that field.

The exact payload shapes are:

```json
{
  "candidate_version": "candidate/v2",
  "candidate_id": "candidate:example",
  "parent_id": "genome:parent",
  "artifact_hash": "<64 lowercase hex>",
  "proposer": "principal:builder",
  "rollback_target": "genome:parent",
  "baseline_capabilities": [],
  "requested_capabilities": [],
  "estimated_cost_micro_usd": 0,
  "metadata": {}
}
```

```json
{
  "evidence_version": "evidence/v2",
  "evidence_id": "evidence:example",
  "subject_candidate_digest": "<candidate-envelope SHA-256>",
  "artifact_hash": "<64 lowercase hex>",
  "check": "unit",
  "status": "pass",
  "verifier": "principal:verifier-a",
  "independent": true,
  "details": {}
}
```

`metadata` and `details` are required explicit objects in v2; omission is not a default.

Schemas are `schemas/v2/candidate.schema.json`, `schemas/v2/evidence.schema.json`,
`schemas/v2/principal.schema.json`, `schemas/v2/identity-context.schema.json`,
`schemas/v2/authorization-context.schema.json`,
`schemas/v2/authority-grant.schema.json`, `schemas/v2/detached-signature.schema.json`, and
`schemas/v2/promotion-input.schema.json`, plus `schemas/v2/attested-proposal.schema.json`. Every payload envelope is composed through
`schemas/v2/envelope.schema.json`. All listed fields are required. No implicit defaults exist;
`null` is allowed only for `previous_snapshot_digest` at sequence zero and the optional grant pair
is omitted as a pair rather than encoded as null.

The project must publish one JSON Schema per payload and per envelope composition. Unknown fields,
unknown kinds, unknown versions, and a payload/schema mismatch fail before signature verification.

## Authority-grant envelope

An authority grant payload has this shape:

```json
{
  "grant_version": "authority-grant/v1",
  "audience": "variaxiom-promotion/v2",
  "trust_domain_id": "trust-domain:example",
  "capability_namespace": "variaxiom-capability/v1",
  "constitution_digest": "<constitution-envelope SHA-256>",
  "lineage_id": "lineage:example",
  "issuer_principal_id": "principal:steward",
  "subject_candidate_digest": "<candidate-envelope SHA-256>",
  "capabilities": ["network.example.com"],
  "not_before_unix_s": 1788739200,
  "expires_at_unix_s": 1788742800,
  "delegable": false
}
```

The grant identifier is `grant:sha256:<digest of the canonical authority-grant envelope>`; it is
not embedded in the hashed payload. The detached signature must be made by a non-revoked key bound
to `issuer_principal_id` with role `authority-issuer`.

For v1, `capabilities` must be non-empty, sorted, unique, and exactly equal to requested
capabilities minus the parent capabilities selected from the anchored authorization context by the
candidate's exact `parent_id`. `delegable` is fixed to `false`. A zero-
delta candidate must omit the grant pair; supplying a redundant grant is invalid. Grant chaining
and delegation require a later protocol version.

Domain, capability namespace, constitution digest, and lineage ID must exactly match the anchored
promotion input. A grant is intentionally not bound to one snapshot digest: after snapshot
rotation it is re-evaluated against the current anchored snapshot and remains valid only if its
issuer/key/role and grant ID are still current and unrevoked. An old promotion input or selector
attestation never remains current merely because the grant can be re-evaluated.

## Detached-signature envelope

```json
{
  "envelope_version": "variaxiom-envelope/v1",
  "kind": "detached-signature",
  "payload": {
    "signature_version": "detached-signature/v1",
    "algorithm": "Ed25519",
    "trust_domain_id": "trust-domain:example",
    "principal_id": "principal:steward",
    "key_id": "key:sha256:<64 lowercase hex>",
    "signed_kind": "authority-grant",
    "signed_digest": "<64 lowercase hex>",
    "signature_base64url": "<86 canonical characters>"
  }
}
```

The Ed25519 message is constructed by ASCII-encoding each validated token and concatenating each
field with one byte `0x0A`, including after the final field:

```text
variaxiom-signature/v1 || 0x0A ||
Ed25519 || 0x0A ||
<trust_domain_id> || 0x0A ||
<principal_id> || 0x0A ||
<key_id> || 0x0A ||
<signed_kind> || 0x0A ||
<signed_digest> || 0x0A
```

`signed_kind` is one of the four values in the role table. `signed_digest` is the SHA-256 identity
of an envelope whose `kind` agrees with `signed_kind`. The verifier must first validate and hash the
target envelope, then reconstruct these bytes itself; it never signs or verifies a caller-supplied
message blob.

The first 31 message bytes are hex
`766172696178696f6d2d7369676e61747572652f76310a456432353531390a`.
Complete golden vectors freeze the full message, key, signature, digest, and result before any gate
integration.

Before signature verification, both runtimes require public key `A` and signature point `R` to be
canonical, decodable, non-identity members of the prime-order subgroup. Python calls
`nacl.bindings.crypto_core_ed25519_is_valid_point` for both points with libsodium 1.0.21 or later,
then PyNaCl `VerifyKey.verify`. Rust decompresses both with maintained `curve25519-dalek`, requires
exact recompression and `EdwardsPoint::is_torsion_free()`, then calls
`VerifyingKey::verify_strict`. Ordinary `verify`, batch verification, prehash, context, and hazmat
APIs are forbidden. Bespoke curve arithmetic is forbidden. Both paths also reject little-endian
`S >= L`, where
`L = 2^252 + 27742317777372353535851937790883648493`. The frozen corpus includes every canonical
encoding of the eight torsion points and mixed-order points as both public key and `R`,
`y >= 2^255-19`, and exact `S=L-1/L/L+1` boundaries. Dependency versions and features are locked; a library change cannot
widen acceptance without a protocol-version change and renewed review.

## Promotion-input/v2 composition

`promotion-input/v2` is a new payload and never replaces a v1 fixture. It commits to:

- the complete candidate envelope and its proposer signature;
- every complete evidence envelope and verifier signature, sorted by evidence ID;
- the complete constitution envelope and its content-addressed artifact hash;
- the trusted identity-context envelope;
- the complete authorization-context envelope;
- an optional complete authority-grant envelope plus its issuer signature;
- the existing deterministic budget, rollback, and policy inputs;
- `protocol_version: "promotion-input/v2"`.

Its exact top-level shape is:

```json
{
  "protocol_version": "promotion-input/v2",
  "candidate": {"envelope": "<candidate envelope>", "signature": "<detached signature envelope>"},
  "evidence": [{"envelope": "<evidence envelope>", "signature": "<detached signature envelope>"}],
  "constitution": {"envelope": "<constitution envelope>", "artifact_hash": "<64 lowercase hex>"},
  "identity_context": "<identity-context envelope>",
  "authorization_context": "<authorization-context envelope>",
  "authority_grant": {"envelope": "<grant envelope>", "signature": "<detached signature envelope>"}
}
```

Angle-bracket strings above stand for complete JSON objects, not JSON strings. `authority_grant` is
omitted only for a zero capability delta and is otherwise required. Evidence pairs are sorted by
`evidence_id`; every other set-like array is lexically sorted and unique. No null/default form is
accepted beyond the explicit identity-context genesis exception.

The input contains objects, not only human-readable IDs. Replacing a key binding, revocation set,
evaluation time, signature, grant, evidence item, or constitution changes the input digest. The
pure promotion decision continues to contain its complete input digest.

Selector signing is a second, acyclic phase. `evaluate_new` returns the exact promotion-input and
decision envelopes but no verified selector claim. An `attested-proposal/v1` envelope carries:

```json
{
  "envelope_version": "variaxiom-envelope/v1",
  "kind": "attested-proposal",
  "payload": {
    "proposal_version": "attested-proposal/v1",
    "promotion_input": "<complete promotion-input envelope>",
    "decision": "<complete promotion-decision envelope>",
    "selector_signature": "<detached signature envelope>"
  }
}
```

Angle-bracket values are complete objects. `verify_attested_proposal` re-evaluates the input against
the current anchor, requires byte-identical canonical decision output, then verifies the selector
signature over the decision envelope. This avoids a digest cycle. M2.1 returns a verified signed
proposal only; it cannot authorize
or perform a durable append. M2.2 must define a promotion-authorization object bound to the exact
expected lineage head and sequence, then enforce an atomic compare-and-swap transaction.

`EvaluatedProposal` is the immutable triple `{verification, promotion_input, decision}` where
`verification.status` is `verified`; `VerifiedProposal` is the pair `{verification,
attested_proposal}` after full re-evaluation and selector verification. Rejection returns only the
verification result and no typed partial output. `ReplayResult` adds `authorizing: false` and the
reproduced decision digest.

## Promotion-input/v2 validation order

Validation is deterministic, fail-closed, and short-circuits at the first failing stage:

1. raw byte-size limit, strict UTF-8/JSON parsing with duplicate-member and depth enforcement, then
   exact raw-byte equality with canonical JSON;
2. envelope version, kind, structural schema, and remaining resource limits;
3. trusted anchor equality for domain, identity-context digest/sequence/time, and complete
   authorization-context digest;
4. target-envelope digest and `key_id` recomputation;
5. global principal/key uniqueness, trusted binding, required roles, role separation, and key
   revocation;
6. strict Ed25519 verification over reconstructed domain-separated bytes;
7. exact evidence-to-candidate digest binding and proposer/verifier independence;
8. grant audience, domain, constitution, lineage, subject digest, capability delta, interval,
   issuer signature, and revocation;
9. exact constitution-envelope digest and content-addressed artifact equality;
10. existing M1.1 evidence, budget, lineage, rollback, and policy checks, using the pinned
    constitution as the only source of cost and verifier thresholds;
11. for `verify_attested_proposal` only: exact decision recomputation and detached selector
    attestation over that decision envelope.

Every failure returns one stable machine code and no partially trusted object. Predicates execute in
the numbered order above. Within one stage, fields follow ASCII-lexical JSON Pointer order and
collection members follow normative sort order; version and kind precede structural schema checks.
Raw wire bytes that differ from `canonical_json(parsed_value)` return `input.encoding_invalid`—M2
does not normalize whitespace, key order, or alternate escapes. Later stages, including
cryptography, do not execute after an earlier failure. Codes below are verifier
results, not promotion-decision policy reasons. Parsers and verifiers expose distinct untrusted and
verified types.

The stage-1/2 predicate-to-code order is exact for independently malformed inputs: oversize raw
bytes → `input.limit_exceeded`; invalid UTF-8, BOM, JSON syntax, or lone surrogate →
`input.encoding_invalid`; duplicate object member → `input.duplicate_member`; depth overflow →
`input.limit_exceeded`; non-canonical raw bytes
→ `input.encoding_invalid`; unsupported envelope/object version → `input.version_unsupported`;
wrong envelope kind → `input.kind_mismatch`; then structural or semantic schema violation →
`input.schema_invalid`. For the trusted-context stage, an identity sequence below the anchor is
`identity.context_stale`; any other domain/digest/sequence/time mismatch is
`identity.context_untrusted`; authorization-context mismatch is
`authorization.context_untrusted`. When one malformed byte stream has multiple parse faults, the
bounded parser returns the first fault encountered; normative fixtures isolate one parse fault per
case so implementation traversal cannot change a promised result.

The remaining predicate order is also exact; each row is exhausted before the next row:

| Stage | Predicate order and stable code |
|---|---|
| 4 | target digest mismatch → `signature.digest_mismatch`; recomputed key ID mismatch → `signature.key_id_mismatch`; signed kind mismatch → `signature.kind_mismatch` |
| 5 | target actor differs from signature principal → `signature.principal_mismatch`; ambiguous identity/key graph → `identity.key_ambiguous`; unknown principal → `identity.principal_unknown`; key not bound to claimed principal → `identity.key_unbound`; cumulatively revoked key → `signature.key_revoked`; cumulatively revoked grant → `grant.revoked`; missing role → `identity.role_missing`; role overlap → `identity.role_conflict`; insufficient distinct principals → `identity.not_independent` |
| 6 | unsupported algorithm → `signature.algorithm_unsupported`; base64/length/non-canonical/non-prime-subgroup point or scalar → `signature.encoding_invalid`; failed Ed25519 equation → `signature.invalid` |
| 7 | evidence candidate digest mismatch → `evidence.subject_digest_mismatch` |
| 8 | audience → `grant.audience_mismatch`; domain/namespace/constitution/lineage → `grant.context_mismatch`; candidate digest → `grant.subject_mismatch`; exact delta → `grant.capability_mismatch`; malformed interval → `grant.interval_invalid`; early → `grant.not_yet_valid`; expired → `grant.expired`; delegation → `grant.delegation_forbidden` |
| 9 | constitution envelope digest mismatch → `constitution.context_mismatch`; artifact content/digest mismatch → `constitution.artifact_mismatch` |
| 10 | deterministic M1.1 evaluation returns its accepted or rejected promotion decision; policy rejection is not a verifier error |
| 11 | recomputed decision differs → `decision.content_mismatch`; then selector signature predicates repeat stages 4–6. The selector field is structurally required, so omission returns `input.schema_invalid` at stage 2. |

When several objects fail the same predicate, normative object order decides: candidate, evidence by
`evidence_id`, grant, then selector. Multi-fault fixtures cover every adjacent precedence pair
whose predicates can fail simultaneously. Mutually exclusive half-open interval branches use
separate exact-boundary fixtures instead.

```json
{"verification_version":"verification-result/v1","status":"rejected","code":"identity.context_untrusted"}
```

Success is `{"verification_version":"verification-result/v1","status":"verified","code":null}`.

## Acceptance criteria

1. Python and Rust derive identical `key_id`, target digest, signing message, detached signature,
   and verification result for RFC 8032 and project fixtures.
2. Changing any canonical target field, signed kind, digest, domain, principal, key, or signature
   fails. Non-canonical whitespace, key ordering, or equivalent escape spellings fail at parsing.
3. Padded/non-canonical base64url, wrong byte lengths, unknown algorithms, and malformed keys fail
   before policy evaluation.
4. A valid signature from an unbound, revoked, or wrong-role key grants no trust or authority.
5. Two keys bound to one principal cannot satisfy proposer/verifier independence.
6. Signed evidence accepts only the exact candidate-envelope digest. A signed grant accepts only
   the exact candidate digest, capability delta, constitution, lineage, trust domain, and capability
   vocabulary.
7. Grants outside `[not_before, expires_at)`, present in `revoked_grant_ids`, or marked delegable
   fail closed.
8. Replaying a valid grant for an adjacent candidate, audience, constitution, lineage, or trust
   domain fails. Under a new anchored snapshot the grant is re-evaluated and remains valid only if
   its issuer binding and role remain current and neither key nor grant is revoked.
9. `promotion-input/v1` fixtures remain byte-for-byte unchanged and continue to pass.
10. Replacing the constitution envelope or artifact under the same human-readable version fails.
11. A selector signature creates only an attested proposal. No M2.1 API can append or activate
    durable lineage; M2.2 additionally requires exact-head/sequence binding and transactional CAS.
12. No test, log, fixture, or artifact contains a non-public key except published RFC 8032 test
    vectors explicitly labelled as non-secret test material.
13. Linux, macOS, and Windows CI plus a clean public clone reproduce all shared vectors and leave a
    clean worktree.
14. A self-minted, swapped, stale, or backdated identity or authorization context cannot authorize new work;
    historical replay is reproducible but explicitly non-authorizing.
15. One key bound to multiple principals, conflicting role combinations, and historical key
    reassignment fail before signature verification.
16. Exact-limit inputs pass and limit-plus-one inputs fail without exceeding the cryptographic
    operation budget.
17. A valid signature from the wrong trust domain fails before key lookup or cryptography, even
    when the same key and principal appear in both domains.
18. Swapping any parent-authority, lineage, artifact, constitution, budget, or verifier-threshold
    fact without changing the relevant pinned authorization-context or constitution digest fails
    before policy.
19. Revoked keys and grant IDs remain revoked through omission and reintroduction attempts across
    at least three later anchor transitions.
20. Canonical mixed-order public keys and signature points are rejected identically before the
    Ed25519 equation in both runtimes.

## Required evidence

- JSON schemas and shared raw/structured fixtures for every new object and failure class;
- Python/Rust exact-byte conformance tests and cross-role adversarial tests;
- mutation, wrong-domain, expired, revoked, replay, alias, and adjacent-scope tests;
- dependency-lock diff and security-focused review of cryptographic API usage;
- a clean-clone verification report naming commit, toolchains, test counts, and fixture digests;
- traceability updates for every linked requirement.

The shared fixture manifest is `fixtures/conformance/v2/manifest.schema.json`. Its entries point to
self-contained case files. Each case records `case_id`, `stage`, exact base64url-encoded input
bytes and their SHA-256, trusted anchor or ordered anchor-transition history, expected stable code,
canonical target digests, signing-message hex, public key, signature, and expected result. The
human-readable base proposal is source material; a runner consumes only the exact canonical bytes
embedded in each case. Both runtimes consume the same manifest. Negative groups include duplicate keys, unknown
fields/version/kind, limits, self-minted/stale identity and authorization contexts, global key
aliasing, role conflicts,
weak/small-order/non-canonical Ed25519 inputs, `S >= L`, Project Wycheproof and mixed-order cases,
wrong domain/principal/key/kind/digest,
missing/extra final LF, non-ASCII signed tokens, padded/standard base64, adjacent candidate fields,
interval boundaries,
revocation, cross-constitution/domain/lineage replay, and redundant grant on zero delta.

## Implementation sequence

1. Freeze schemas, signing-message bytes, stable codes, and shared fixtures with no gate changes.
2. Add parse/validate/verify types in Python and Rust; keep signing helpers outside the trusted
   verifier path.
3. Differentially test both runtimes, including invalid library edge cases and unchanged M1.1.
4. Introduce the explicit `promotion-input/v2` verifier behind a disabled-by-default local feature;
   it returns an attested proposal and exposes no append capability.
5. Defer exact-head promotion authorization and durable CAS to M2.2.
6. Repeat independent clean-clone reproduction and automated security-council review before
   enabling v2 by default.

## Rollback and compatibility

M1.1 objects and fixtures remain supported and unchanged. M2.1 adds new object kinds and
`promotion-input/v2`; it does not reinterpret v1. Before any public release, rollback removes the
v2 entry point and signature-aware activation while retaining rejected/experimental v2 artifacts
as auditable evidence. After a public v2 release, incompatible changes require new versions.

Revocation is monotonic across anchor history; removing an ID from a later embedded snapshot cannot
remove it from the trusted anchor. Revocation never deletes earlier signatures. Historical replay uses the recorded anchor and always
returns `authorizing: false`. New authorization uses only the separately trusted current anchor and
trusted time.

An issuer, selector, or trust-anchor compromise triggers an operator-controlled emergency freeze:
disable `evaluate_new` and `verify_attested_proposal`, preserve the last trusted lineage head,
publish a later snapshot that
revokes affected keys and outstanding grants, rotate to new globally unique keys, and resume only
after the new snapshot digest/sequence/time is pinned. Backdated objects created after compromise
cannot pass the new anchor; historical replay remains labelled non-authorizing.

## Review gates before implementation

- complete the independent automated security-council re-review tracked in
  [issue #5](https://github.com/artemiosu/variaxiom/issues/5) for this specification and ADR 0010;
- confirm Python/Rust library behavior on the shared invalid-signature corpus;
- name the authority-issuer and promotion-selector trust roots for tests only;
- resolve how production key custody is delegated without adding secrets to the repository.

The council is defense in depth, not proof of security. Its report names reviewer roles/models,
reviewed commit, conflicts, findings, remediation mapping, residual risks, and unanimous verdict.
GitHub Copilot review may add another signal but cannot alone satisfy this gate.
