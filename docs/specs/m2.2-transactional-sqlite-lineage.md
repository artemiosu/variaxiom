# M2.2 — Transactional SQLite lineage and deterministic projections

**Status:** accepted by the [three-role automated council](../reports/m2.2-specification-council-2026-09-12.md)
at exact revision `6f267e049f0e944a264ed988af2dd623d0dbab22`; not a human security audit
**Requirements:** REQ-CORE-001, REQ-CORE-002, REQ-CORE-003, REQ-PROM-001,
REQ-PROM-002, REQ-LINE-001, REQ-LINE-002, REQ-ROLL-001, REQ-ROLL-002,
REQ-OPS-001, REQ-OPS-002, REQ-OPS-003, REQ-OBS-001, REQ-REP-001, REQ-REP-002
**Trust boundary:** operator-controlled writer handle → Rust constitutional kernel → one local
SQLite database → non-authorizing readers and outbox consumers
**Authority impact:** critical; this is the first increment allowed to append an already verified
promotion result to durable germline history. It does not deploy or activate candidate code.

## 1. Problem

M2.1 can authenticate and reproduce a promotion decision, but every result is deliberately
non-authorizing. A valid proposal is evidence, not permission to mutate lineage. M2.2 must define
the separate operator-controlled write boundary and make an accepted promotion durable without
allowing stale writers, retries, crashes, projection corruption, or caller-supplied decisions to
silently change the selected lineage.

The contract must be precise enough that an independent Python oracle and the Rust writer produce
the same event bytes, hashes, receipts, stable failures, selected head, and rebuilt projections.

## 2. Security invariants

1. Possessing candidate bytes, a signature, an M2.1 result, or a database path is not authority to
   write. Only a Rust writer handle injected by the trusted host can begin a lineage transaction.
2. The writer consumes raw M2.1 attested-proposal bytes and a separately supplied live trusted
   anchor. It re-runs the complete M2.1 verifier inside the write operation. It never accepts a
   caller-supplied decision, digest, or `VerifiedProposal` as a substitute.
3. Every mutation compares the exact global event head. A mutation of a lineage head also compares
   that lineage's exact generation, selected genome, and selecting event hash.
4. An event append, decision/object storage, head change, rollback reservation, request receipt,
   projection update, and outbox enqueue either commit in one SQLite transaction or do not become
   visible at all.
5. Authoritative events are immutable and hash-linked from genesis. No M2.2 API updates, deletes,
   compacts, renumbers, or silently repairs them.
6. While the exact writer authorization and control lease remain valid, a retry with the same
   request ID and byte-identical canonical operation input returns the stored receipt without
   repeating effects. After pause, revocation, epoch change, or expiry, the same historical receipt
   remains available only through a verified read-only session. Reusing the request ID with any
   different command, anchor, immutable recorded time, authorization, or writer epoch fails closed;
   the fresh per-attempt authority-check clock may advance without changing operation identity.
7. Rejected promotion decisions remain append-only evidence but never change the lineage head or
   create a rollback reservation.
8. Every accepted promotion selects the exact candidate artifact and reserves its verified
   rollback target in the same transaction.
9. Rollback is an explicit operator-authorized transition. It appends history and never erases the
   failed or superseded lineage.
10. Projections are disposable views. Rebuilding them from genesis must yield byte-identical
    canonical rows at the same event head; mismatch stops writes.
11. Downstream/application effects and telemetry export occur only after SQLite reports a successful commit and
    the resulting store root is durably published by exact external-root CAS. A future outbox
    delivery worker is required to use at-least-once delivery, and consumers deduplicate by
    immutable outbox ID; M2.2 itself guarantees only atomic enqueue and the dispatch gate. The
    protocol-required `prepare_exact` pending-intent CAS and the best-effort local R23 recovery
    security-audit attempt are control-plane parts of the commit/recovery protocol, not
    downstream/application effects or ordinary telemetry export; they are governed by their own
    abort/recovery and non-authorizing audit rules.
12. A receipt proves that its SQLite transaction committed. The exact external-root finalization
    and authoritative transition are proved either by an outer `LineageOperationResult` with
    `status:"committed"`, or after recovery by a verified `StoreOpenResult` with status `opened` or
    `recovery_resolved` whose byte-identical expected/observed root includes that receipt's event
    and whose root custodian has no pending intent. The accompanying language-level carrier grants
    only the separately authorized read/write capabilities. Every receipt/result remains
    `authorizing: false`; it cannot authorize another transition.
13. Database, WAL, and shared-memory files are one integrity unit on one local host. Copying,
    moving, or restoring only the main file while a live WAL exists is forbidden.
14. No candidate-controlled SQL, table name, path, PRAGMA, migration, clock, or retry policy reaches
    SQLite.
15. A general writer opens only after full lineage/projection verification against an
    operator-retained external store root. The sole initialization-only writer requires the exact
    directly verified empty pre-genesis state. An internally valid but older replacement database
    cannot reopen for writes.
16. Trusted-anchor state either stays byte-identical or advances through every exact M2.1
    transition. Sequence jumps, forks, ownership changes, and revocation removal fail closed.
17. The sole writer capability is bounded by an operator identity, store/lineage/domain scope,
    control epoch, expiry, and permission set. Pause/revoke linearizes against commit and stale
    handles cannot write.

## 3. Scope

- one local SQLite database and one Rust writer;
- exactly one lineage and trust domain per database in v1;
- canonical append-only lineage events and content-addressed protocol objects;
- exact-head compare-and-swap for global history and selected lineage state;
- durable accepted and rejected M2.1 decisions;
- explicit initialization, promotion commit, and rollback commands;
- explicit operator-authorized trusted-anchor advancement;
- immutable idempotency receipts;
- rollback reservations;
- transactional outbox rows with no delivery worker in this increment;
- deterministic read projections and offline rebuild/compare;
- operator-retained store roots and verified artifact-retention manifests;
- schema-version and forward-only migration policy;
- bounded fault injection at every transaction step;
- vendor-neutral local telemetry hooks emitted after commit.

## 4. Non-goals

- deployment, canarying, process restart, tool loading, or activation of candidate code;
- PostgreSQL, distributed consensus, replication, Kafka, Kubernetes, or a remote object store;
- private-key custody or signing; candidate-driven key rotation or trust-anchor amendment;
- network filesystems, shared-cache mode, `ATTACH`, loadable extensions, triggers, or caller SQL;
- external delivery; this contract stops at atomic enqueue plus a root-gated handoff, while a
  future worker must use at-least-once delivery;
- event deletion, mutation, compaction, automatic repair, or in-place history rewriting;
- online destructive migration or downgrade;
- accepting a prior Python/Rust success object as authority;
- Python access to the production write connection.

## 5. Normative terminology and encodings

The words **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are normative. M2.1 canonical JSON,
strict UTF-8, token, safe-integer, digest, and maximum-depth rules remain in force. Every new
top-level content-addressed protocol object named as an envelope in section 7 uses
`variaxiom-envelope/v1`, has an explicit payload version, rejects unknown fields, and must arrive
as exact canonical bytes with no trailing newline. The exact nested head/facts/projection-row
values, public result evidence objects, and outbox message defined later are deliberate bare closed
objects, not envelopes; their own displayed shape and version field are normative. Schema authors
MUST NOT wrap those explicit exceptions or infer any additional exception.

An event hash is lowercase SHA-256 of the complete canonical `lineage-event` envelope. The hash is
not embedded in the envelope it identifies. A command digest, receipt digest, checkpoint digest,
and object digest use the same SHA-256-over-canonical-envelope rule. SQLite integers remain within
the M1.1 interoperable safe range even when SQLite could store larger values.

The database ID is precomputable before initialization: `store:sha256:` plus lowercase SHA-256 of
`b"variaxiom-store/v1" || 0x00 || UTF8(store_slot_id)`. The operator must allocate a globally unique,
stable store slot and never reuse it for another database. The byte formula is frozen before
schemas. The ID never depends on a command, authorization, schema migration, event, or mutable path.

`null` is used only where a shape explicitly permits it. Omission is never an implicit default.
Arrays whose meaning is a set are lexically sorted and unique. Event order is protocol order and
must never be sorted.

## 6. Authority boundary and public operations

The trusted host opens a database path from operator configuration and injects four non-candidate
capabilities: an `OperatorWriteAuthority`, an `ExternalRootStore`, a read-only `ArtifactResolver`,
and a shared `ControlLatch`. The root store returns an owned `ExpectedStoreRoot` snapshot. Only
after full store verification may the kernel construct an opaque,
non-serializable and non-cloneable `LineageWriter`. Candidate, evaluator, Python, plugin, model,
and protocol bytes cannot construct or receive these values. Filesystem permissions and process
isolation enforce this boundary; arbitrary code execution in the trusted host remains a critical
out-of-scope compromise.

`OperatorWriteAuthority` has a privately constructed canonical descriptor with this exact closed
envelope:

```json
{
  "envelope_version": "variaxiom-envelope/v1",
  "kind": "writer-authorization",
  "payload": {
    "authorization_version": "writer-authorization/v1",
    "authorization_id": "writer-auth:operator-chosen-token",
    "operator_principal_id": "principal:operator",
    "store_slot_id": "store-slot:operator-configured-token",
    "database_id": "store:sha256:<precomputed database digest>",
    "lineage_id": "lineage:example",
    "trust_domain_id": "trust-domain:example",
    "allowed_operations": ["initialize_lineage"],
    "control_epoch": 4,
    "not_before_unix_s": 1789084700,
    "expires_at_unix_s": 1789088400
  }
}
```

The displayed object is the exact initialization-only variant. `allowed_operations` is a sorted
unique subset of `advance_trusted_anchor`, `commit_evaluation`, `initialize_lineage`,
`read_lineage`, `recover_pending_root`, and `rollback_lineage`. `read_lineage` can open only a
verified read-only session and can never yield a writer or mutate/finalize an external root. Every
authority, including initialization-only,
binds the exact precomputed database ID. After initialization the host may issue a broader authority
bound to that same ID. Anchor changes require the distinct
`advance_trusted_anchor` permission; `commit_evaluation` never implies it. The operator-configured
`store_slot_id` binds the pre-initialization capability without placing a filesystem path in
protocol identity. The descriptor digest is
recorded in every operation and event. The authorization interval is structurally valid only when
`not_before_unix_s < expires_at_unix_s`; a recorded seconds value is inside it exactly when
`not_before_unix_s <= recorded_at_unix_s < expires_at_unix_s`, and an attempt millisecond value is
inside it exactly when `not_before_unix_s * 1000 <= authority_check_now_unix_ms <
expires_at_unix_s * 1000`, with the checked conversion defined below. Equality to the converted
expiry therefore returns the stage-1 `operator.authorization_expired` result before any monotonic
deadline is constructed, while a value below the converted not-before boundary returns
`operator.authorization_not_yet_valid`.
The private authority constructor refuses a structurally invalid interval and exposes no store API
result. Encountering such a descriptor in retained authoritative replay state is
`store.integrity_failed` and trips the `HealthLatch` when a session exists.
Possession of descriptor bytes is not sufficient to
construct the capability. The host control plane has two related mechanisms. A `ControlLease`
registers one active open/mutation/recovery operation from its first predicate check through its
capability-free terminal return, or transfers only into a still-running sealed open cursor; it
retains its epoch/deadline but does not prevent pause/revoke. A short
`ControlCommitGuard` serializes pause/revoke with each protected COMMIT or root-store CAS: its
acquisition atomically rechecks `ControlLatch`, `HealthLatch`, epoch, permission, and deadline and issues one sealed,
single-use `EffectPermit` bound to that exact COMMIT/CAS input. The guard is released before the
potentially blocking effect; pause/revoke acquires the same guard only to change state and never
waits for an artifact, SQLite, root lock, or admitted effect. If permit issuance wins, that effect's
authority linearizes before the competing pause/revoke and may finish afterward; if pause/revoke
wins, guard acquisition issues no permit and the effect cannot start. The writer
checks epoch/expiry plus both latches before verification, after acquiring the SQLite writer lock, and
immediately before `COMMIT`. A committed receipt remains available through the read-only lookup
after revocation, but no write operation—including an absent retry—can use a stale handle.
`EffectPermit` is the collective name for four private, non-serializable, non-cloneable newtypes:
`PrepareRootPermit`, `SqliteCommitPermit`, `AbortRootPermit`, and `FinalizeRootPermit`. Every permit
binds the operation digest, pending-intent digest, private active-lease registration ID, control
epoch, and absolute phase deadline. Prepare additionally binds the expected root and root-phase ID;
COMMIT binds the private SQLite connection/transaction generation, exact receipt digest, and
resulting event hash; abort binds the expected root and root-phase ID; finalize binds both expected
and resulting roots plus its root-phase ID. Each target method accepts only its matching private
permit type and consumes it exactly once, so a permit from another step cannot compile as an
argument and caller bytes cannot substitute it. Guard issuance and target-method entry form one
non-yielding kernel call path: the guard is released and the permit is synchronously moved directly
into that method with no caller callback, task suspension, queue, or API return between them. Host
scheduler preemption after issuance does not revoke an effect whose authority already linearized;
a platform/runtime that cannot preserve this direct ownership path cannot enable the writer. No
permit is a wire object or durable authority record.
The handle is not cloneable, but its trusted host may submit concurrent calls through one shared
borrow; the handle serializes them internally before any SQLite transaction or root-store intent.
Initial `ControlLease::try_register` runs under the same control-state guard: it rejects a set
maintenance barrier as the existing ordered stage-1 `operator.paused` predicate, or returns the
first other failed stage-1 control predicate; otherwise it increments the active-lease
count before releasing the guard. Maintenance sets the no-new-leases barrier and observes the
active count under that same guard, then releases it before waiting for zero. Thus registration
either precedes the barrier and is awaited, or follows it and fails; no operation can enter between
the zero observation and maintenance ownership. The barrier is cleared under the same guard only
after maintenance has released every artifact, SQLite, and root resource; new registrations cannot
race the tail of maintenance.
On every terminal API return, including deferred or unknown outcomes, all admitted calls must first
establish that no later effect can linearize and atomically deregister the active `ControlLease`.
Only a still-running partial-open operation transfers that registration into its sealed
`StoreOpenCursor`; cursor drop/expiry deregisters it. A successful capability-bearing open instead
retains the `StoreSnapshotLease` and creates a distinct private `StoreSessionLease` bound to the
verified root, authorization scope/control epoch, and configured session deadline, then
deregisters the open-operation `ControlLease` before returning. Future mutations must atomically
`try_register` their own active `ControlLease`; the writer session is necessary context but never a
substitute. Every read checks its session lease, `ControlLatch`, `HealthLatch`, and epoch; closing, expiry, pause, or epoch
change invalidates its views. Capability-free results release all leases before return. Thus no
terminal result or idle session leaks the active-operation count, while sessions remain bounded and
the durable pending intent/artifact hashes preserve recovery state after the operation lease is
gone.

The supervisor assigns every dedicated storage-process instance one private monotonically fresh
`StorageProcessGeneration`. Every session, cursor, session-operation/control lease, effect permit,
maintenance barrier ownership record, request message, and response is bound to exactly that
generation. Watchdog exit or any child-process death atomically marks the generation dead and
closes its transport before handling another message. The supervisor rejects every late response,
invalidates all generation-bound capabilities/cursors, prevents new admission, cancels and joins
in-flight host calls, and releases/deregisters each in-process lease, active count, snapshot token,
and maintenance barrier exactly once only after OS process termination proves no later file/root
activity. The triggering call and any call that had entered the dead child return no API result;
an idle stale proxy fails locally with `storage.interrupted` and can never reconnect. A restarted
child receives a fresh generation and cannot issue any reader/writer/cursor until complete
store-open verification and pending-intent recovery. No response or permit from an older generation
is accepted by the new child or supervisor.

When the trusted host first constructs an operation, it snapshots immutable
`recorded_at_unix_s`. Every execution attempt separately snapshots fresh
`authority_check_now_unix_ms` and a monotonic clock in one `ControlLease`. The fresh wall value is
an exact trusted Unix-millisecond reading, not a rounded or truncated seconds value. The immutable recorded
time is reused byte-for-byte after an unknown outcome; the fresh authority-check time is never
part of operation identity. The private authority constructor checked-multiplies
`not_before_unix_s` and `expires_at_unix_s` by 1,000 into exact millisecond boundaries; operation
construction does the same for `recorded_at_unix_s`. An unrepresentable authority is refused before
an API capability exists, and an unrepresentable retained value is latched integrity failure.
`authority_check_now_unix_ms` MUST be greater than or equal to the converted recorded time; the
recorded seconds value and fresh millisecond value MUST each fall within the original operation's
half-open writer-authorization interval during a normal mutation attempt. After those interval
checks, the lease computes
`remaining_ms = expires_at_unix_ms - authority_check_now_unix_ms` and
`authority_deadline_tick_ms = checked_add(monotonic_now_tick_ms, remaining_ms)` in the frozen u64
millisecond domain; either overflow invokes the global storage-generation-death/no-result rule.
Later checks use the current
monotonic clock against that fixed deadline and recheck the control epoch plus both latches. Successful
`ControlCommitGuard` issuance of an exact `EffectPermit` immediately before an external-root CAS is
the authority linearization point for that CAS. If it passes, the already-authorized atomic CAS and durability
work may finish after the deadline; no new operation or root transition may linearize after it.
Pause/revoke may complete after permit issuance while the already-admitted effect is in progress;
this orders after that effect's authority decision and does not retroactively cancel it. A legitimate retry therefore neither backdates the authority check nor changes its
idempotency identity. For evaluation, the M2.1 live anchor time equals immutable
`recorded_at_unix_s`, not the later retry clock. A host that supplies a false trusted time is an
out-of-scope trusted-host compromise.

Pending-root recovery uses a new separately scoped recovery authority. For a proven committed
one-event extension, it revalidates the retained operation's recorded time against the original
writer-authorization descriptor stored with that event, while only the fresh attempt time must fall
inside the new recovery authority's millisecond-converted half-open interval. The fresh time must
still be greater than or equal to
`checked_mul(stored_recorded_at_unix_s, 1000)`; conversion overflow in retained state is
`store.integrity_failed`, not a rounded comparison. For a proven SQLite non-commit, those operation objects need not exist:
safe `abort_exact` instead requires the exact retained pending intent, byte-identical expected
external root, unchanged fully verified database, absent request/receipt, and a fresh current
`recover_pending_root` authority scoped to the same store/database/domain/lineage. Aborting that
uncommitted intent records no event and makes no claim about its old recorded time. A later recovery
grant therefore cannot rewrite committed event time, but its newer not-before bound does not make
an older legitimate pending operation unrecoverable.

The stage-1 `operator.authority_check_before_recorded` predicate applies only to a direct mutation,
where both times are separate owned API inputs before SQLite is opened. In committed pending-root
recovery, stored recorded time is not trusted until the exact event, operation envelope, and
original authorization descriptor have passed full integrity verification. Only then is the same
relation checked as stage-2 `operator.recovery_check_before_recorded`; any malformed, missing, or
inconsistent retained source wins earlier as `store.integrity_failed`. Proven-noncommit abort has
no stored recorded-time predicate.

`ExpectedStoreRoot` is operator-retained outside the SQLite database and has this exact closed
canonical envelope:

```json
{
  "envelope_version": "variaxiom-envelope/v1",
  "kind": "store-root",
  "payload": {
    "store_root_version": "store-root/v1",
    "store_slot_id": "store-slot:operator-configured-token",
    "database_id": "store:sha256:<precomputed database digest>",
    "schema_digest": "<64 lowercase hex>",
    "event_head": {
      "head_version": "event-head/v1",
      "sequence": -1,
      "event_hash": null
    },
    "projection_checkpoint_digest": null
  }
}
```

The displayed object is the exact pre-initialization root. A post-initialization root retains the
same database/store-slot/schema identity and requires a non-negative/non-null event head plus a
non-null checkpoint digest.
`expected_store_root_digest` always means SHA-256 of the complete canonical envelope. On
reopen, the store slot and database must equal the root. The sole exception is the exact one-event
extension named by the retained pending intent; after full receipt/root verification it returns
non-authorizing `store.root_advance_required` evidence and no writer until finalization. A database
that is byte-identical to the retained root while the exact pending receipt is absent returns
non-authorizing `store.pending_recovery_required` evidence and no writer until abort. A database
behind or divergent from the retained root returns `store.rollback_detected`; an extension without
that intent returns `store.unrecognized_extension`. The in-memory session advances its root after
each confirmed root finalization and the receipt carries the next exact root. The external root is
a store-open precondition,
not an event-identity input: changing only a stale expected root cannot change the bytes of an
otherwise identical operation, while its command head and separately bound trusted inputs still
identify the exact transition.

`ExternalRootStore` is a separately protected, non-cloneable host capability with only
`load_owned()`, `prepare_exact(...)`, `finalize_exact(...)`, `abort_exact(...)`, and the bounded
admission read/sync primitive `confirm_durable_exact(...)`. Every `load_owned()` and owned reload
runs as a synchronously cancellable `RootReadPhase` with a private absolute deadline equal to the
earlier of its enclosing open/root-phase/maintenance deadline and
`checked_add(monotonic_now, 30,000 ms)`. It must start while `now < deadline`; equality is expired.
Completion and cancellation share one private atomic terminal state: root bytes may be published
to the verifier only if completion claims that state with a trusted timestamp strictly before the
deadline. Equality/expiry wins cancellation, and a losing late completion is discarded and cannot
influence any result.
An initial-open deadline returns rejected `storage.interrupted`; ordinary root I/O failure returns
rejected `storage.io_error`, and no unverified root bytes enter `expected_store_root`. A reload
after a CAS result maps timeout/I/O/unprovable state to that CAS row's existing unknown code.
The storage supervisor must synchronously cancel a pre-linearization read and prove no lingering
task before return; if a blocked backend cannot be cancelled by the deadline, it terminates the
dedicated storage process with no API result and the next invocation restarts verified recovery.
A platform that cannot guarantee termination and no later read-side ownership/resource use keeps
the writer disabled. Before SQLite
commit, it permits at most one exact pending operation with this closed canonical envelope:

```json
{
  "envelope_version": "variaxiom-envelope/v1",
  "kind": "store-pending-operation",
  "payload": {
    "pending_version": "store-pending-operation/v1",
    "expected_store_root_digest": "<digest>",
    "operation_digest": "<digest>",
    "command_digest": "<digest>",
    "writer_authorization_digest": "<digest>",
    "control_epoch": 4,
    "expected_event_head": "<complete event-head/v1>",
    "resulting_event_hash": "<digest>",
    "resulting_store_root_digest": "<digest>",
    "outbox_id": "outbox:sha256:<digest>",
    "artifact_hashes": ["<sorted unique raw-artifact digest>"]
  }
}
```

`artifact_hashes` is the following exact sorted unique operation set, independent of whether a
positive lease exists:

- initialization: genesis and operator-reason artifacts plus the initial authorization context's
  constitution artifact and every verified-artifact hash;
- anchor advancement: the next authorization context's constitution artifact and every
  verified-artifact hash;
- accepted evaluation: candidate and evidence artifacts, the current selected artifact that
  becomes the rollback target, and the current authorization context's constitution artifact and
  every verified-artifact hash;
- rejected evaluation: exactly the same evaluation reference set (including the observed current
  selected artifact and current authorization-context artifacts), represented by every key in its
  exact artifact-retention manifest, including observations with status
  `unavailable_at_verification`, `unretained_digest_mismatch`, `unretained_limit`, or
  `unretained_quota`;
- rollback: current selected, target, and operator-reason artifacts.

No other digest enters this array. An implementation never infers membership from filesystem
availability, pin reuse, or whether a positive lease happened to exist.
`prepare_exact` is an atomic CAS from `(expected root digest, no pending intent)` to that exact
intent. `finalize_exact` is an atomic CAS from `(same root, same pending intent)` to `(resulting
root, no pending intent)`. `abort_exact` is an atomic CAS from `(same root, same pending intent)` to
`(same root, no pending intent)` and is permitted only after the kernel proves that the SQLite
transaction did not commit. Each successful transition durably writes through a same-filesystem
temporary file, file `fsync`, atomic rename, and parent-directory `fsync` before returning. An
unknown prepare/finalize/abort outcome write-blocks the session and permits only exact recovery.
Each prepare, abort, or finalize phase snapshots one absolute 5,000 ms monotonic
linearization-admission deadline and an exact maximum of eight CAS attempts immediately before its
first `ControlCommitGuard` attempt. Every CAS retry in that phase requires a fresh guard admission
and fresh single-use `EffectPermit` and must begin before both that phase deadline and the active authorization deadline; prepare must also
remain inside the transaction-admission deadline. Abort after proven non-commit and finalize after
confirmed commit do not reuse the expired transaction deadline. If no CAS linearized by the phase
deadline, any currently admitted pre-linearization attempt is synchronously cancelled and proved
no-effect. If eight definite-no-effect attempts complete first, no ninth attempt starts. Either
exhaustion path returns the applicable definite-no-effect/deferred result. If the atomic rename
linearized before its deadline,
the permitted call remains synchronously owned until its file and directory durability work
finishes or becomes unprovable and may return after 5,000 ms, but never beyond the separate
30,000 ms storage-effect completion watchdog. Crossing that hard watchdog terminates the dedicated
storage process without an API result; subsequent startup treats it exactly as process death and
resolves SQLite/root state from retained evidence. A platform that cannot synchronously cancel
pre-linearization work, supervise/terminate the storage process, and guarantee that no logical root
transition can occur after termination cannot enable the writer. An unprovable
post-linearization durability outcome maps prepare/abort to `storage.intent_publish_unknown` and
finalize to `storage.root_publish_unknown`.
For deadline accounting, a CAS attempt "begins" exactly when its matching
`ControlCommitGuard` successfully issues the permit; target-method entry is the direct non-yielding
continuation of that already-admitted attempt and is not a second clock boundary.
At target-method entry, the supervisor snapshots that effect's absolute storage-completion
deadline as `checked_add(monotonic_now, 30,000 ms)` before performing any VFS or root-store work.
The worker completion and watchdog share one private atomic terminal state. Completion may claim
that state and return only when its trusted completion timestamp is strictly less than the absolute
deadline; equality belongs to the watchdog. At or after the deadline the supervisor atomically
claims termination if completion has not already won, terminates the dedicated storage process,
and emits no API result. A completion observed at the same boundary cannot race to a different
language-specific result. Process isolation must also guarantee that termination leaves no
background logical transition; otherwise the writer remains disabled.
On every return, the CAS linearization is guaranteed either already to have occurred or never to
occur; no background rename/state transition may happen later. `unknown` means only that an
already-past linearization/durability outcome cannot be observed, not that an in-flight mutation is
released to continue. The active lease and single-use effect permit remain owned by the call until
this property is established; the short control guard itself is already released.
Post-linearization durability work may finish after its admission deadline only while the
permitted call still owns that completion; it cannot create a later state transition after
return.
Definite no-effect always triggers an owned reload and this closed matrix:

| CAS | Reloaded state | Result |
|---|---|---|
| `prepare_exact` | expected root + byte-identical pending intent | idempotent prepare success |
| `prepare_exact` | expected root + no pending intent | fresh permit per retry within root-phase, authorization, and transaction deadlines; exhaustion rolls back and returns `concurrency.external_root_mismatch` |
| `prepare_exact` | any other fully read state | roll back SQLite, invalidate writer, `concurrency.external_root_mismatch` |
| `prepare_exact` | reload unavailable/unprovable | `storage.intent_publish_unknown` |
| `abort_exact` | expected root + no pending intent | idempotent abort success |
| `abort_exact` | expected root + byte-identical pending intent | fresh permit per retry within root-phase and authorization deadlines; exhaustion returns `storage.intent_abort_deferred` |
| `abort_exact` | any other fully read state | `storage.root_state_conflict` |
| `abort_exact` | reload unavailable/unprovable | `storage.intent_publish_unknown` |
| `finalize_exact` | resulting root + no pending intent | idempotent finalize success |
| `finalize_exact` | expected root + byte-identical pending intent | fresh permit per retry within root-phase and authorization deadlines; exhaustion returns `storage.root_publish_deferred` |
| `finalize_exact` | any other fully read state | `storage.root_state_conflict` |
| `finalize_exact` | reload unavailable/unprovable | `storage.root_publish_unknown` |

`storage.root_state_conflict` is a non-authorizing outcome-unknown result: SQLite may already have
committed, the writer remains blocked, and only a fresh recovery open may classify the externally
observed foreign/divergent state. No CAS miss is silently treated as success outside the two exact
idempotent rows above.
Every idempotent-success row additionally calls `confirm_durable_exact` under the same non-resetting
root-phase admission deadline. If confirmation cannot start before that deadline, the phase returns
the CAS-specific unknown code. Once admitted, its owned file/directory sync may finish after the
deadline, just like post-linearization durability, but remains subject to the same 30,000 ms
process watchdog and cannot leave background work after return or supervised termination. It
reopens and byte-compares the exact custodian state, synchronizes
that file and its parent directory, and re-reads equality before success. A fully read unequal
state is `storage.root_state_conflict`; unavailable or unprovable I/O retains the unknown mapping
for that CAS (`storage.intent_publish_unknown` for prepare/abort and
`storage.root_publish_unknown` for finalize). Byte equality alone never enables COMMIT, ACK, or
outbox dispatch.

After SQLite commits, the lineage session remains write-blocked until finalization succeeds. Only
then may it return `status:"committed"` or expose the outbox event to a dispatcher. If the process
dies, reopening fully verifies the database and external state: unchanged database plus absent
receipt permits aborting the exact pending intent; an exact one-event extension plus verified
receipt/resulting root permits finalization; an extension without the matching retained intent, a
different extension, or more than one event is `store.unrecognized_extension` and never yields a
writer or root-advance suggestion. During the live mutation, failure to prove the outcome returns
`storage.intent_publish_unknown`, `storage.commit_unknown`, `storage.root_state_conflict`, or
`storage.root_publish_unknown` with
`status:"outcome_unknown"` according to the unresolved step. `storage.commit_unknown` is never an
open-result code: a later open either proves receipt presence/absence and then resolves the exact
intent, or rejects with `storage.io_error`/`store.integrity_failed` without claiming an outcome.
Once SQLite state is proven during open, only an uncertain root-store abort/finalize can return
`storage.intent_publish_unknown` or `storage.root_publish_unknown`; a failed final authority check
or exhausted definite-no-effect retry budget before a completed abort returns
`storage.intent_abort_deferred`, while the corresponding finalize condition returns
`storage.root_publish_deferred`. A database copy equal to the
last retained root is therefore allowed to forget only an operation that was never acknowledged or
dispatched as committed.

Terminology is strict: a successful SQLite COMMIT with an unresolved root intent is
`sqlite_committed_pending`, not an acknowledged or externally authoritative committed operation.
When `read_lineage` is independently authorized, it may be inspected through the bounded borrowed
`RecoveryReader` exposed by a `RecoveryReadSession`, but that non-authorizing evidence cannot
be dispatched or treated as a retained-root commitment. The authoritative commit point is
successful exact external-root finalization. Before that point no success, writer reuse, outbox
handoff, downstream/application effect, or ordinary telemetry export is allowed; the protocol's
pending-intent/root-custodian CAS and best-effort local R23 recovery audit attempt are the
explicitly governed control-plane exceptions. Recovery may forget only the exact unacknowledged
pending SQLite commit under the rules above.

`open_verified_store` may finalize or safely abort a recognized pending intent only when the supplied authority
contains the distinct `recover_pending_root` permission and passes a fresh control lease. It
recomputes the receipt and exact resulting root, calls `finalize_exact` for a proven one-event
extension, or calls `abort_exact` for a proven absent transaction. Immediately before either CAS it
acquires a `ControlCommitGuard`, which rechecks the control epoch, both latches, monotonic deadline,
permission, and exact pending intent and issues a single-use permit; permit issuance is the
authorization linearization point. The guard is released, and only that permit can invoke the exact
atomic root-store CAS. Failure performs no root-store mutation. A successful check may
be followed by durability completion after the deadline as defined above. It reloads the root and
derives the return carrier only from permissions other than the consumed recovery permission:
`Opened` for `read_lineage` plus an applicable mutation, `ReadOnlyOpened` for `read_lineage` only,
`WriteOnlyOpened` for an applicable mutation only, or capability-free `RecoveryResolved` when no
read or mutation permission remains. `recover_pending_root` never implies `read_lineage`. Without recovery
permission, a proven absent transaction returns `PendingRecoveryRequired`, while a proven exact
one-event extension returns `RootAdvanceRequired`; either carrier includes a
`RecoveryReadSession` if and only if `read_lineage` is also present, otherwise it carries evidence
only. That session exposes only a borrowed `RecoveryReader`. The operator can
therefore inspect the state only under the distinct read permission and re-open with properly
scoped recovery authority. `read_lineage`
alone yields only `ReadOnlyOpened` on a fully verified clean initialized store and only the
appropriate recovery-required evidence/carrier when a pending intent exists; it cannot resolve
that intent. It never accepts a caller-supplied replacement root.

Pre-genesis recovery is a closed special case. With no pending intent, only the exact
initialization permission set `{initialize_lineage}` can yield `InitializationReady`; every other
scope rejects `operator.operation_not_allowed`. If an
initialization attempt published an intent and then proved no SQLite commit, reopening for
automatic abort requires the exact combined set `{initialize_lineage,recover_pending_root}`. After
the durable abort it re-verifies the empty root and returns `InitializationReady` with the same
initialization-only writer restriction. In that pending-intent state, any other valid scope receives
`PreInitializationRecoveryRequired` and no reader/writer because no lineage exists. If the
initialization did commit, the normal one-event recovery rules finalize it and then return an initialized
carrier under the same exact permission matrix. On a later clean reopen, the exact combined
`{initialize_lineage,recover_pending_root}` scope retains only the initialization-retry capability
described next; the now-inapplicable recovery permission neither widens that capability nor yields
`RecoveryResolved`.

An initialized clean store opened with either exact scope that can originally receive an
initialization writer—`{initialize_lineage}` or
`{initialize_lineage,recover_pending_root}` after a proven pre-genesis abort—is the sole
post-genesis exception: it returns `InitializationRetryReady` with a sealed
`InitializationRetrySession` only when the current authorization descriptor digest and control
epoch match and its complete canonical descriptor bytes are byte-identical to the immutable
writer-authorization object retained for the genesis event. Otherwise open rejects
`operator.operation_not_allowed`. The sealed session binds the genesis request ID and
initialization operation digest. It can invoke only `initialize_lineage`, only to resolve a
lost response for the original finalized initialization. The operation performs the normal
authority and immutable-input checks, then its read-only idempotency lookup. A byte-identical
request/operation returns the stored initialization receipt; the same request with different
operation bytes returns `idempotency.conflict`; any other request returns
`lineage.already_initialized` without querying unrelated request rows and before quota reservation,
artifact work, pending-intent publication,
or any SQLite/root mutation. The session is single-use, has the same bounded lifetime and private
view rules as `InitializationSession`, and cannot call any other mutation or read API. No broader
scope containing `initialize_lineage` acquires this exception; its independently
applicable read/mutation permissions determine the ordinary initialized carrier.

Recovery authorization attribution is an explicit M2.2 v1 operational limitation. The lineage
event and receipt retain the original operation writer; a later recovery authority cannot rewrite
those facts. The host MUST emit a structured non-authorizing security audit record containing the
pending-intent digest, abort/finalize action, recovery principal, recovery-authorization digest,
control epoch, attempt time, and observed outcome. That telemetry is not a germline event or an
integrity proof and its loss cannot reinterpret the root transition. A durable,
root-custodian-bound recovery audit log is required before production operations claim attributable
recovery and is tracked as R23; it is deliberately outside the M2.2 writer/schema freeze.

The global acquisition order is atomic session/cursor-use admission → active `ControlLease`
registration (for mutation/recovery) → artifact GC/retention lease →
SQLite writer lock → short `ControlCommitGuard`/permit issuance → external-root CAS. The commit guard is exempt
from an inversion cycle because pause/revoke holds it only for a bounded in-memory state change and
never acquires or waits for any later resource. Maintenance installs a no-new-leases barrier under
that guard, releases it, then waits for the active-lease count to reach zero before acquiring
artifact/SQLite/root resources; it never waits for an active operation while holding the guard.
Store opening loads and releases the root snapshot before touching SQLite;
maintenance never holds the root-store lock while waiting for SQLite. After COMMIT the SQLite
writer lock is already released before external finalization. These rules prevent lock inversion.
Session close/expiry takes only the private session-state lock to close admission and never waits
while holding it; maintenance does not acquire that lock and instead waits for the bounded
`StoreSnapshotLease` after the admitted call count drains.

`ArtifactResolver` opens a sealed store-wide `ArtifactSnapshotLease`, then accepts only digests and
returns `Present(ArtifactLease)` with the exact immutable-handle byte length, `Unavailable`, or
`LookupFailed` for each lookup; it exposes no
caller path lookup. `Unavailable` means only a successful authoritative namespace lookup proving
that the digest is absent. Permission failures, interrupted reads, malformed backing state, and
other I/O failures return `LookupFailed` and map to stage-4 `artifact.io_error`; they can never be
recorded as a rejected artifact's `unavailable_at_verification` observation.
The 30,000 ms aggregate artifact-resolution deadline starts immediately before the first namespace,
index, metadata, lookup, open, or read operation and is passed into every resolver call. Every such
call MUST return or cancel without a later background effect by that deadline; a platform without
bounded/cancellable artifact I/O cannot enable the writer. Before hashing, the resolver reads the
immutable namespace index for exactly the sorted-unique operation union in lexical digest order,
checks every exact stored length, and checked-sums the in-bound lengths. More than 268,435,456 present raw bytes across one
operation rejects with `artifact.operation_limit_exceeded`; this predicate precedes digest reads.
It hashes each in-bound object through a bounded streaming reader without loading the whole file and
checks the same aggregate monotonic deadline before and after every at-most
1,048,576-byte chunk. Deadline or interrupted-read failure maps to retryable `artifact.io_error`.
A required oversized artifact
rejects with `artifact.limit_exceeded`; rejected-promotion evidence records the bounded status
defined below. The snapshot lease retains the shared namespace/GC lock,
while each present lease retains owned immutable metadata. The resolver opens and closes at most
one streaming file handle at a time in lexical order; the namespace lease prevents replacement,
deletion, or content mutation from the first positive or negative lookup until SQLite rollback or
confirmed SQLite commit plus external-root publication. The writer records
a durable pin in its transaction. Artifact creation uses a same-filesystem temporary file, file
`fsync`, atomic rename, and parent-directory `fsync`; publication of a new digest takes the same
exclusive namespace-mutation lock as GC. M2.2 exposes no deletion operation; any later cleanup
must take that exclusive lock and honor every committed pin before unlinking. A process
death releases the in-process lease immediately, so cleanup must also consult the durable external
pending intent and retain every digest in its `artifact_hashes` array until that intent is finalized
or safely aborted after database recovery. Thus every possible committed reference is covered by
either the live lease, durable pending intent, or committed pin.
Each database/store slot has exactly one artifact namespace and exactly one external-root custodian;
the namespace refuses a second custodian binding. Its cleanup path reads that custodian's pending
intent under the same maintenance lease, so no unenumerated pending source can be skipped.

Opaque capabilities/cursors never appear in canonical evidence, cannot be caller-constructed, and
are returned only by their matching enum variant. The schema/fixture phase freezes both exact
evidence bytes and compile-fail/API-surface tests for these carrier variants.
Every capability-bearing `StoreOpenOutcome` owns exactly one private non-cloneable session. A
session exposes only lifetime-bound borrowed `LineageReader`, `RecoveryReader`, or `LineageWriter`
views applicable to its variant; those views cannot outlive, detach from, or close independently of
the session. Each API call must first atomically obtain a private non-cloneable
`SessionOperationLease` from the session. This changes the session's active-call count only when
its state is open and its absolute deadline has not been reached. Close/expiry atomically changes
the state to closing, rejects every later admission, and signals cancellation to admitted reads;
it releases the underlying `StoreSnapshotLease` only after the last admitted operation or retained
read cursor has completed/cancelled and established that no later work can occur. The last
`SessionOperationLease` performs that release. Thus logical expiry is immediate while physical
snapshot release cannot race a call already using it. The session owns no active control-operation
registration between calls.
Every read return uses a private `ReadCompletionGuard` over the control state followed by the
session state. It atomically rechecks pause/epoch, `ControlLatch`, `HealthLatch`, session generation, and `now <` both session
and read deadlines, then either marks the call complete and publishes its evidence/retained cursor
or discards tentative evidence under the read-result order below. A success that wins this claim is
linearized before a later close/pause/epoch change and may finish returning; pause/epoch/
`ControlLatch`/session invalidation or exact deadline equality that wins first returns
`storage.interrupted`, while a remaining `HealthLatch` failure returns
`store.integrity_failed`. The same state transition releases
the call lease or transfers it into the returned partial read cursor, eliminating a
check-to-return gap.
`VerifiedReadView` is a public sealed trait with a private supertrait, implemented only by
`LineageReader` and `RecoveryReader`; external code cannot implement it. The three read functions
accept a borrowed `VerifiedReadView`, so their exact API covers both approved reader types without
letting either type yield a writer or widen its originating session scope.
`InitializationSession` and `InitializationRetrySession` are distinct sealed types and are not
`VerifiedReadView`; neither can be substituted for a general writer session.

All four mutation operations require the writer handle and their own exact permission.
Read-only operations accept a reader issued by the same verified store session. Their optional
continuations are distinct lifetime-bound, non-serializable Rust `LineageVerificationCursor` and
`ProjectionVerificationCursor` types with private fields,
created only after verifying the complete prefix from genesis. Caller bytes can never construct or
resume either cursor; restart begins again from genesis unless an operator-retained verified checkpoint is
supplied as the expected root. A partial result can never claim full verification.
Each partial read cursor retains its originating `SessionOperationLease`; resume either atomically
continues that exclusive use or, if still idle when close/expiry wins, fails
`input.cursor_invalid`. Cursor
drop/error/completion releases it. No session timer releases the physical snapshot out from under
an admitted resume. An idle cursor has a private absolute expiry no later than its originating
session deadline. Expiry atomically consumes and invalidates an idle cursor, releases its retained
`SessionOperationLease`, and, when it is the last admitted use, releases the physical snapshot;
an abandoned cursor therefore cannot block maintenance. If resume admission wins the same atomic
boundary strictly before expiry, the admitted call owns the lease until its completion guard;
idle/unadmitted exact equality is expiry and returns `input.cursor_invalid`. Only a resume admitted
strictly before expiry that later loses its completion guard to session invalidation or deadline
returns `storage.interrupted`.

Store opening is likewise bounded. A partial `open_verified_store` call returns no reader or
writer, only a lifetime-bound sealed `StoreOpenCursor` bound to the owned database identity,
external-root snapshot, observed immutable head, verified prefix, reducer state, configuration,
authority/control epoch, and original monotonic deadline. The cursor retains the same active
`ControlLease` registration and owns one continuous SQLite read snapshot plus an operator-enforced exclusive `StoreSnapshotLease` over the protected database,
WAL, connection registry, and file-generation identity. Every Variaxiom open/write/backup/migration
and test fault injector must acquire that lease; raw access that bypasses it is a trusted-host or
deployment compromise. Supplying the cursor to the same operation continues at the next event in
that same snapshot. Resume rechecks cursor lifetime, file/inode/WAL generation, configuration,
root/head, and snapshot identity before reading; mismatch rejects, trips the `HealthLatch` where integrity
is implicated, and rereads no untrusted continuation. After the final verified row, the admitted
resume call first closes/resets the physical SQLite verification snapshot under the applicable
open deadline or bounded cleanup phase while continuously retaining its cursor admission,
`ControlLease`, and exclusive `StoreSnapshotLease`. It holds no control/cursor state lock during
that supervised SQLite/VFS work, publishes no capability, and permits no other open, resume, or
file mutation. Failure to prove closure returns the applicable capability-free
result under the non-mutation close/reset mapping: deadline/cancellation is
`storage.interrupted`; CORRUPT/NOTADB/FORMAT/SCHEMA is latched `store.integrity_failed`; every
other timely non-OK or context-invalid status—including BUSY/FULL/NOMEM/CONSTRAINT/ROW/DONE—is
`storage.io_error`. The post-BEGIN/COMMIT mapping in section 18 does not apply to open/read close or
reset. The same narrow non-mutation mapping governs every open/read `ConnectionControl`, `Prepare`,
`BindOrStatementControl`, and `ReadStep` call: a deadline-driven `SQLITE_INTERRUPT` is
`storage.interrupted`; an integrity primary is latched `store.integrity_failed`; and every other
timely non-OK or context-invalid status is `storage.io_error`. Only failure of the initial database
connection/path open with primary `SQLITE_CANTOPEN`, `SQLITE_PERM`, or `SQLITE_READONLY` maps to
stage-2 `store.open_failed`; those primaries at any later adapter call map to `storage.io_error`.
The complete extended integer is diagnostic only, so all extended forms follow their primary.
Inability to prove that
no file/lock task remains causes supervised process death with no API result. Only after snapshot closure
and absence of lingering VFS work is proved may a private `OpenCompletionGuard` take the control
state followed by cursor state and atomically claim one terminal outcome. Success requires
`now <` the cursor/authority deadlines and unchanged `ControlLatch`/`HealthLatch`/epoch/barrier/root/snapshot identity; in
this guard the root and snapshot comparisons use only the cursor's already-owned immutable values
and generation counters protected by its continuously held `StoreSnapshotLease`. It performs no
SQLite, filesystem, root-custodian, or other blocking I/O while holding either state lock. In that
same indivisible transition it transfers the active `StoreSnapshotLease` into a new private
`StoreSessionLease`, installs the replacement session
timer, marks the cursor consumed, and deregisters the open-operation `ControlLease`. A success that
wins is linearized before later invalidation and may finish returning the new session; a
pause/expiry/epoch change or exact deadline equality that wins first discards it and returns the
applicable rejected outcome and releases the retained leases; the already-closed snapshot is never
resumed. Thus no file mutation can occur in the gap and no idle session counts
as an active operation. At that successful final recheck, the session replaces
the open-cursor timer with a new non-extendable deadline equal to the earlier of the unchanged
authorization expiry and `now + opened_session_deadline_ms`; exactly,
`active_authority_deadline_tick_ms` is the retained authority deadline for direct completion and
`min(retained_authority_deadline_tick_ms, fresh_continuation_authority_deadline_tick_ms)` for resumed
completion, after which `session_deadline_tick_ms = min(active_authority_deadline_tick_ms,
checked_add(open_completion_monotonic_tick_ms, opened_session_deadline_ms))`. Overflow follows the
global generation-death/no-result rule before the session is exposed. This never extends authority. Its
independent expiry handle owns the exact close path. A capability-free result releases both leases
and deregisters before return. The cursor cannot be serialized,
constructed by caller bytes, transferred to another store session, or resumed after its original
operator-configured `open_verification_deadline_ms`. That value is frozen in store configuration,
lies in `30,000..=3,600,000`, and is independent of the shorter per-reader invocation deadline.
Each continuation supplies a fresh `authority_check_now_unix_ms` and must still pass the same
authority/`ControlLatch`/`HealthLatch`/epoch checks without registering or reacquiring a second control lease, but it cannot extend the cursor's original monotonic deadline; the
effective deadline is the earlier of the retained open deadline and the fresh continuation-derived
authority deadline computed from the unchanged original authorization expiry.
The cursor is non-cloneable and its private state atomically admits at most one resume call. Drop
closes admission, cancels any admitted read, and releases both leases only after that read reaches
its next per-event cancellation check. A trusted host timer owns an independent expiry handle. At
the original deadline it atomically closes admission; when idle it immediately closes the SQLite
snapshot through the bounded cleanup phase and releases/deregisters both leases, while an active resume retains them until the
cancelled call proves no later work and performs the same release. An idle expired cursor supplied
later is `input.cursor_invalid`; expiry that loses the admission race to a resume yields rejected
`storage.interrupted` with no replacement cursor. Exact deadline equality belongs to expiry.
Process restart begins
at genesis. No general writer exists until complete verification and projection comparison reaches
the head. The sole pre-genesis exception is `InitializationReady`: the kernel directly verifies
the pre-initialization external root, schema metadata, global `(-1,null)` sentinel, null created
event/checkpoint, absence of every authoritative/projection/lineage/request/outbox row, absence of a
pending intent, and an initialization-only authority bound to the precomputed database ID. It then
returns only a writer capable of `initialize_lineage`, never a general reader or another mutation.
No canonical projection exists before event zero; after initialization, ordinary full replay and
projection equality are mandatory and this carrier is unreachable.

The session shares a one-way in-memory `HealthLatch`. Any integrity or projection mismatch trips
it; every writer checks it before and after acquiring the write lock. Reopening requires full
verification against the external root and creates a new `HealthLatch`. No public generic SQL or
transaction callback is exposed. Python implements only the fixture oracle, receipt/event parser,
and offline rebuild in a temporary database; it is not a production writer.
SQLite primary `SQLITE_CORRUPT`, `SQLITE_NOTADB`, `SQLITE_FORMAT`, or `SQLITE_SCHEMA`, including
their extended forms, is an integrity-indicating result under this fixed-schema profile. Detection
atomically trips the shared `HealthLatch` and invalidates the current session before cleanup or
outcome classification. No same-session retry/read result may proceed; only a new full verified
open against the external root can create another `HealthLatch`. Before external pending-intent prepare,
the stable rejection is the rechecked stage-2 `store.integrity_failed`, whether the latch was
already set at initial validation or won concurrently at a later pre-prepare checkpoint. After prepare, the invalidated session
cannot issue an abort/finalize permit or trust a local receipt-absence lookup: a directly proven
pre-COMMIT rollback/non-commit retains the pending intent and returns stage-10
`storage.intent_abort_deferred`; after an unconfirmed COMMIT attempt, or whenever non-commit is not
directly provable without trusting the damaged store, it returns stage-10
`storage.commit_unknown`. A separately confirmed successful COMMIT follows the
pre-finalization `storage.root_publish_deferred` branch below.
At every mutation/effect guard or completion boundary, the operator `ControlLatch` and session
`HealthLatch` are distinct predicates. Ordered `ControlLatch`/authorization failure keeps
its stage-1 operator code. A winning `HealthLatch` before pending-intent prepare invalidates the
session and returns stage-2 `store.integrity_failed`; it is never collapsed to
`storage.interrupted`. After prepare but before any COMMIT attempt, including a COMMIT guard that
does not issue a permit, it proves/rolls back local non-commit without trusting new store evidence,
retains the unchanged pending intent, attempts no abort CAS, and returns stage-10
`storage.intent_abort_deferred`. After an unconfirmed COMMIT attempt it returns
`storage.commit_unknown`. After a separately confirmed successful COMMIT but before root
finalization it returns `storage.root_publish_deferred`. At one boundary snapshot, ordered control
failure wins first, then `HealthLatch`, then the applicable session/deadline/BUSY predicate.
`HealthLatch` is stage 2 only before a pending intent; after prepare its corresponding path-specific
stage-10 abort-deferred/commit-unknown/root-publish-deferred carrier supersedes an ordinary
stage-2 or stage-5 code. No
`HealthLatch`-invalidated session may obtain prepare/COMMIT/abort/finalize permits.
Pending-intent recovery remains write-blocked until a new full verified open proves the exact
committed/noncommitted state; failure of that verification remains `store.integrity_failed` and
requires operator-controlled restore rather than append.

The host supplies immutable `recorded_at_unix_s` when constructing every operation and fresh
`authority_check_now_unix_ms` for every execution attempt; the kernel does not read the wall clock.
Only the latter drives the current writer-authorization and control-lease checks. For promotion,
the M2.1 live anchor still supplies the authoritative evaluation time and its
`trusted_now_unix_s` must exactly equal `recorded_at_unix_s`; the recorded time and owned anchor
digest enter operation identity. Initialization, anchor advancement, and rollback copy
`recorded_at_unix_s` into the event. A retry reuses the recorded time but refreshes the authority
check; changing the recorded time conflicts, while changing only the attempt clock does not.

For the M2.1 cross-spec requirement, the byte-exact `lineage-evaluation-command` together with one
invocation through the scoped opaque `LineageWriter` is the `promotion-authorization/v1` boundary.
The command binds the expected event/lineage heads and proposal; the writer capability supplies the
operator/store/domain/epoch/expiry permission. Neither component is reusable as authorization on
its own. The canonical `lineage-operation-input/v1` envelope is the retained, content-addressed
promotion-authorization object required by M2.1: it commits the exact command/head, owned live
anchor, writer-authorization descriptor, control epoch, and immutable recorded time while excluding
the fresh per-attempt check time. Its digest, rather than either component alone, is committed by
the event and receipt.

observation has this exact closed shape; every nullable field is required:

```json
{
  "envelope_version": "variaxiom-envelope/v1",
  "kind": "artifact-observation",
  "payload": {
    "observation_version": "artifact-observation/v1",
    "requested_artifact_hash": "<digest>",
    "status": "pinned",
    "was_already_pinned": false,
    "observed_size_bytes": 4096,
    "observed_size_lower_bound_bytes": null,
    "observed_sha256": "<digest>",
    "pinned_count_before": 2,
    "pinned_count_after": 3,
    "pin_count_limit": 16384,
    "pinned_bytes_before": 8192,
    "pinned_bytes_after": 12288,
    "pin_limit_bytes": 4294967296
  }
}
```

The relations are exact:

- `pinned`: exact size and matching observed digest, null lower bound, byte after-total equal to the
  before-total for an existing unique pin or before plus size for a new pin, and count after-total
  equal to count before for an existing pin or before plus one for a new pin;
- `unavailable_at_verification`: allowed only for a never-pinned digest, with all observed byte
  fields null and unchanged count/byte totals;
- `unretained_digest_mismatch`: allowed only for a never-pinned in-bound object, with exact size,
  a nonmatching observed digest, null lower bound, and unchanged count/byte totals;
- `unretained_limit`: allowed only for a never-pinned object, with null exact size/digest,
  lower bound `67,108,865`, and unchanged count/byte totals;
- `unretained_quota`: allowed only for a never-pinned in-bound object with exact matching digest
  and size whose checked addition would exceed either count limit `16,384` or byte limit
  `4,294,967,296`; both after-totals remain unchanged.

Every observation requires constant `pin_count_limit:16384` and
`pin_limit_bytes:4294967296`. The first observation's before-count/bytes equal the verified
`artifact_pin_totals` values at operation start; each after-count/bytes equal the next entry's
before-count/bytes; the final after-count/bytes equal the transaction's resulting totals.
Observations are produced in manifest order under the artifact snapshot lease and retained as
canonical writer-attested historical evidence. Replay validates their bytes, relations, manifest,
event binding, and external-root commitment; it does not pretend that later filesystem state can
independently prove an earlier absence, corrupt byte sequence, or quota snapshot. If a digest was
already permanently pinned, unavailability or oversize is `store.integrity_failed` before aggregate
admission; digest invalidity is the same integrity failure after aggregate admission and therefore
is not evaluated when the bounded operation itself already exceeds that earlier aggregate limit.
Either reached integrity failure trips the `HealthLatch` and appends no event.

All fact shapes are closed and versioned in the schema/fixture phase. Sequence zero requires a
null previous hash. Sequence `n > 0` requires the hash of event `n-1`. The stored `event_hash` must
equal the digest of canonical envelope bytes, and the stored indexed columns must equal decoded
payload fields. Gaps, duplicates, alternate bytes, and dangling previous hashes are corruption.
Event `recorded_at_unix_s` must be greater than or equal to the prior event's value; sequence, not
time, remains the authoritative order.

An event never embeds the digest of a reservation keyed by its own event hash; doing so would make
the hash graph cyclic. After computing the event hash, the writer deterministically constructs the
reservation from that hash and the event facts: initialization uses a null target, acceptance uses
the complete previous lineage head, and rollback uses `next_rollback_target_lineage_head`. The
receipt then binds the resulting reservation digest. Verification reconstructs and checks this
same acyclic order.

### 9.1 Transition matrix

| Path | Required prior state | Event | Lineage head | Decision/anchor | Reservation |
|---|---|---|---|---|---|
| Initialize | schema plus global `(-1,null)` sentinel; no authoritative rows | sequence 0, null previous hash | insert generation 0 with supplied genesis genome/artifact | store M2.1 genesis anchor and contexts; no decision | create null-target reservation keyed by event 0 |
| Advance anchor | initialized; exact global expectation and stored prior anchor | next sequence, previous global hash | read and return unchanged; no lineage CAS | store exact M2.1 `advance_anchor` output; no decision | none; prior reservation unchanged |
| Accept | initialized; exact global and lineage expectations; live anchor equals stored | next sequence, previous global hash | CAS to generation +1 and `genome:sha256:<candidate digest>` | store recomputed accepted decision; anchor unchanged | create reservation to complete previous lineage head |
| Reject | initialized; exact global expectation; command lineage expectation null; live anchor equals stored | next sequence, previous global hash | read and return unchanged; no lineage CAS | store recomputed rejected decision; anchor unchanged | none; prior reservation unchanged |
| Roll back | initialized; exact global/head expectations and current reservation | next sequence, previous global hash | CAS to generation +1 and reserved target | no decision/anchor change | consume current reservation and create new event-keyed reservation copied from restored target |

All five paths create one request row, one event, one compact outbox row, updated projection state,
and one receipt. Only initialization/acceptance/rollback change the selected lineage head. Only
initialization and the dedicated anchor-advance path change stored trusted-anchor state. The
complete operation is still one SQLite transaction.

The receipt field matrix is also closed:

| Path | decision digest/status | recorded anchor | previous/resulting lineage head | consumed/resulting reservation | lineage changed |
|---|---|---|---|---|---|
| Initialize | null / null | resulting initialized anchor | null / generation-zero head | null / new null-target reservation digest | true |
| Advance anchor | null / null | resulting advanced anchor | current / byte-identical current | null / null | false |
| Accept | recomputed digest / `accepted` | exact unchanged live anchor | current / generation-plus-one head | null / new previous-head reservation digest | true |
| Reject | recomputed digest / `rejected` | exact unchanged live anchor | observed current / byte-identical observed current | null / null | false |
| Roll back | null / null | null | current / generation-plus-one restored head | consumed current digest / new event-keyed reservation digest | true |

Every row has non-null `resulting_lineage_head`, outbox ID, event identity, previous/resulting store
roots, and `sqlite_committed:true`, `effects_dispatched:false`, `authorizing:false`. This receipt
field proves only the SQLite transaction observed through a borrowed `RecoveryReader`; the outer result reaches
`status:"committed"` only after exact external-root finalization. The schema/fixture
phase freezes every null, constant, and relational constraint in this matrix.

### 9.3 Read-only result shapes

`StoreOpenResult` is exactly

sessions shown in the table.
`recovery_resolved` proves that this invocation durably resolved an exact pending intent but grants

snapshot through the bounded cleanup phase, and returns `storage.interrupted`; equality with the absolute session deadline is
expired. A latched integrity failure that remains after the ordered interruption predicate returns

return differently across implementations.

value is `input.limit_exceeded` before any row is consumed. Each verified event consumes exactly one
unit. An invocation consumes at most `work_limit` events and checks session/control validity plus
one absolute trusted monotonic read deadline before the first event and after every completed
event. After an event, owned-head
completion wins first; otherwise a reached deadline returns rejected `storage.interrupted`, closes
the snapshot through that cleanup phase, and returns no cursor; otherwise exhaustion of `work_limit` returns a partial carrier
with the actual next sequence. A work-limit partial cursor retains the same snapshot and original
deadline, and must be resumed before that deadline. Thus slow zero/nonzero-progress reads reject
rather than emitting an already-expired cursor. Fixture clocks freeze exact boundary/tie schedules;
elapsed time never enters canonical evidence.

The sealed operational clock exposes an abstract unsigned 64-bit millisecond tick in
`0..=18,446,744,073,709,551,615`. Every storage-process generation has its own origin; all
capabilities/deadlines are generation-bound, so ticks are never compared across generations. A
production adapter converts elapsed host-monotonic duration since that origin to whole milliseconds
by checked floor conversion and fails the generation if the value is unrepresentable. The Python
oracle must enforce the same u64 domain despite arbitrary-precision integers. The fake-clock
fixture surface can inject every exact tick, including values near the maximum.

Every absolute monotonic deadline in this contract uses checked u64-millisecond arithmetic, including authority,
open/cursor/session/read, root-read/root-CAS, pre-transaction/BEGIN/transaction/COMMIT,
storage-effect watchdog, maintenance, and cleanup deadlines. Arithmetic overflow is identical to
fatal exhaustion of the storage process generation: no corresponding call, effect, barrier,
cursor, session, transaction, or result is admitted/exposed after detection. The supervisor
terminates that generation before any activity governed by the newly constructed deadline can
start, returns no API result, rejects late messages, and applies the exact process-death lease
cleanup and verified restart rules in section 6. Any SQLite/root state acquired by an earlier
deadline phase is abandoned to that process-death rollback/recovery; SQLite rolls back an
uncommitted transaction on process loss, and a retained pending intent is resolved only by the
normal fresh recovery open. Neither saturating arithmetic nor an
unbounded Python integer may extend the range. Exact overflow/process-death vectors are required
for every named deadline constructor, including construction while SQLite or a pending intent is
already held.

## 10. SQLite profile

All SQLite open/prepare/step/read/write/sync calls run inside the same supervised dedicated
storage process and are synchronously cancellable at the applicable absolute deadline. Store open
uses its retained open deadline; receipt/verification/projection reads use the 30,000 ms read
deadline; mutation SQLite access before `BEGIN IMMEDIATE` uses a non-resetting 30,000 ms
pre-transaction SQLite deadline snapshotted immediately before its first SQLite call; statements
after `BEGIN IMMEDIATE` use the 10,000 ms transaction deadline atomically derived from the winning
guard's exact trusted completion timestamp as defined in section 12. For every open/read/mutation
deadline, the sole post-expiry exception is a non-resetting SQLite cleanup/classification phase
with its own 30,000 ms absolute deadline, snapshotted when cleanup begins. Every path may interrupt,
finalize/reset statements, close snapshots/connections, and release locks; mutation outcome
classification may additionally roll back, call `get_autocommit`, reopen read-only, and look up the
exact receipt. It cannot publish read evidence, issue an authoritative write, start a new
transaction, or COMMIT. Session/control expiry never prevents local cleanup, although the
separate external-root abort still requires its own fresh permit. A call starts only while
`now < deadline`; equality is expired. If cancellation completes with no lingering VFS task, the
closed result is `storage.interrupted` subject to pending-intent cleanup. If a blocked VFS call
cannot be synchronously cancelled at the deadline, the supervisor terminates the storage process
with no API result; restart performs the same verified crash recovery used for process death. A
platform/VFS that cannot guarantee no continued file or lock activity after termination cannot
enable the writer. SQLite progress handlers remain defense in depth and are not treated as a bound
on blocked VFS calls. Every supervised non-COMMIT SQLite/VFS call uses the same private atomic
terminal arbitration as `RootReadPhase`: only completion with a trusted timestamp strictly before
the applicable deadline may publish rows/status; equality belongs to cancellation, late bytes are
discarded, and an uncancellable loser triggers process death with no result.

## 12. Transaction algorithm

The following order is normative. One stable outer code is returned; `cause_code` preserves an
exact M2.1 failure where applicable.

1. Atomically `try_register` and retain a new active `ControlLease` from the fresh
   `authority_check_now_unix_ms` through the operation's capability-free terminal return, after
   atomically obtaining the matching session's `SessionOperationLease`, and evaluate every stage-1
   authority predicate in the stable table, or
   fail its exact code. Bound raw command bytes, strict-parse canonical JSON, enforce
   version/kind/schema, snapshot all inputs into owned bytes, and compute `command_digest` and the
   full `operation_digest` from immutable `recorded_at_unix_s` without opening a write transaction.
   A session close/deadline that wins the atomic operation-admission race returns
   `storage.interrupted` before caller bytes or stage-1 predicates are evaluated and creates no
   `ControlLease`. Once admission wins, the operation retains its session lease through every
   cleanup/deferred/unknown boundary; close/expiry prevents later protected-effect admission but
   cannot release the physical store snapshot beneath that operation.
2. Require either (a) a healthy general store session whose full event/projection state was
   compared with the operator-retained external root at open and which has no pending root intent,
   or (b) solely for
   `initialize_lineage`, the exact `InitializationReady` session that directly verified the closed
   empty-state/root/schema/sentinel predicates in section 6, or (c) solely for a post-genesis
   `initialize_lineage` retry, the exact `InitializationRetrySession` described above. The two
   initialization carriers are single-use and cannot run another operation. Validate database
   application ID, schema version, required PRAGMAs and shared
   `HealthLatch`. These integrity checks precede receipt lookup; mutable capacity does not.
3. Perform a read-only idempotency lookup. Equal request ID and operation digest returns the stored
   receipt only after its digest, event, and head-independent invariants verify. Different digest
   returns `idempotency.conflict`. For any `initialize_lineage` invocation against an initialized
   store, including one through `InitializationRetrySession`, an absent/unbound request returns
   `lineage.already_initialized` immediately. On this path it is a special stage-3 terminal
   predicate after idempotency conflict/success and before every stage-4 quota, anchor, proposal,
   or artifact predicate. Only any other absent request proceeds; before expensive verification it
   must reserve the configured directory quota and free-space margin or return
   `store.quota_unavailable`.
4. For initialization or dedicated anchor advancement, run the corresponding M2.1 anchor
   operation. For evaluation, require byte-identical stored/live anchor state, then run the complete
   Rust M2.1 `verify_attested_proposal` against the owned live anchor and independently recompute the
   decision. After classification, resolve required artifacts through bounded leases and
   stream-verify their exact raw-byte length and SHA-256 while holding the shared GC lock through
   transaction outcome/root publication. Initialization, anchor advancement, acceptance, and
   rollback freshly resolve every required raw artifact under the snapshot lease and require it to
   be present, within bounds, digest-valid, and covered by a valid permanent pin in the resulting
   transaction. An existing pin avoids duplicate accounting/insertion but never skips byte
   verification. Rejection retains all
   protocol evidence, leases and pins every retainable referenced artifact, and records a sorted
   unique immutable artifact observation for each digest plus their retention-manifest object.
   Status is exactly `pinned`,
   `unavailable_at_verification`, `unretained_digest_mismatch`, `unretained_limit`, or
   `unretained_quota`; the artifact-store lock
   covers the availability/size/quota observation, and the label intentionally makes no claim about
   later creation. Unretained statuses are valid only for never-pinned rejected-only digests; a
   missing or oversized existing pin is `store.integrity_failed` before aggregate admission. After
   the reference-count and aggregate-byte predicates pass, a digest-corrupt existing pin is
   `store.integrity_failed`; an aggregate-byte failure deliberately wins before digest streaming.
   An unretained raw artifact
   does not erase a verified policy rejection. Before lookup, an exact operation reference union

### SQL compare-and-swap

The frozen SQL must be equivalent to:

```sql
UPDATE event_head
SET sequence = :next_sequence, event_hash = :next_event_hash
WHERE singleton = 1
  AND sequence = :expected_sequence
  AND event_hash IS :expected_event_hash;
```

and, for a lineage transition:

```sql
UPDATE lineage_heads
SET generation = :next_generation,
    genome_id = :next_genome_id,
    artifact_hash = :next_artifact_hash,
    selected_by_event_hash = :next_event_hash
WHERE lineage_id = :lineage_id
  AND generation = :expected_generation
  AND genome_id = :expected_genome_id
  AND artifact_hash = :expected_artifact_hash
  AND selected_by_event_hash = :expected_selecting_event_hash;
```

For initialization only, the lineage CAS is an `INSERT ... SELECT ... WHERE NOT EXISTS` guarded by
the sentinel global head and exact database/lineage emptiness, and it must insert one row. The
single-writer lock is not a substitute for either comparison. A stale command that obtains the
lock still fails. CAS misses roll back all rows created by that attempt.

## 13. Idempotency and concurrency

`request_id` is scoped to one database forever in v1, is 1–128 ASCII bytes, and is supplied by the
trusted caller. The database never generates it. The first committed command binds it to the exact
operation digest, command digest, and receipt. Rows are never expired or reused in M2.2.

- same request ID + same operation digest: return exact stored receipt; append count is unchanged;
- same request ID + different operation digest: `idempotency.conflict`, regardless of head state;
- new request + stale event head: `concurrency.event_head_mismatch`;
- new accepted/rollback request + current event head but stale lineage head:
  `concurrency.lineage_head_mismatch`;
- two concurrent calls through the same thread-safe but non-cloneable writer session are serialized;
  at most one commits for one expected global head, and the loser retries only after constructing a
  new operator-approved command with the new expected head;
- every outcome-unknown code—`storage.intent_publish_unknown`, `storage.intent_abort_deferred`,
  `storage.commit_unknown`, `storage.root_state_conflict`, `storage.root_publish_deferred`, or
  `storage.root_publish_unknown`—write-blocks the original writer and is never retried through a
  mutation API. A fresh open fully proves SQLite receipt presence/absence and root state. A
  retained matching pending intent requires `recover_pending_root` authority to finalize, abort, or
  report it; an already-completed exact abort/finalize with no pending intent may open normally
  under otherwise valid read/mutation scope. Recovery binds the retained request ID,
  operation digest, command digest, immutable recorded time when committed source objects exist,
  original authorization/control epoch, and live anchor where applicable; it never reconstructs a
  different operation.

The original receipt is returned even if later events, revocations, or projections change. That is
historical evidence, not current authority.
Mutation-API retry applies only to an already finalized operation with no pending intent, while the
exact writer authorization/control lease remains valid; its stage-3 lookup returns the stored
receipt without repeating effects. After pause, revocation, epoch change, or expiry, that finalized operation
is inspected only through a separately scoped `read_lineage` authority and `read_receipt`; this
returns historical evidence without exercising the stale write capability. Any retained pending
intent instead requires a fresh `recover_pending_root` authority, optionally combined with
`read_lineage` for later inspection. This rule also applies to initialization response loss after
the lineage exists; pre-genesis loss follows the closed recovery matrix in section 6.

## 14. Rollback semantics

Every selecting event has one immutable `rollback-reservation/v1` envelope keyed by that event.
Genesis uses a null target. An accepted promotion's reservation targets the complete previous
lineage head named by the candidate's verified rollback target. A rollback command succeeds only
when:

- the exact current head was selected by `failed_event_hash`;
- the reservation for that event exists and exactly matches target genome/artifact;
- the target artifact bytes still hash correctly;
- the target has an earlier valid selecting/initialization event in the same lineage;
- the operator reason artifact exists and hashes correctly.

The rollback event increments the global sequence and lineage generation, selects the reserved
target, and retains all failed events and objects. In the same transaction it creates a reservation
keyed by the new rollback event whose target is copied exactly from the historical reservation
associated with the restored target's selecting event. A null historical target remains null and
makes further rollback unavailable. The rollback event and receipt bind both consumed and new
reservation digests. Rollback has no implicit retry under a new head and never triggers deployment.

The artifact pin manifest includes every external artifact digest referenced by any committed
event or retained proposal/evidence object: genesis, accepted or rejected candidate evidence,
rollback targets, and operator reasons. Retainable artifacts are permanently pinned even for a
policy-rejected decision; an explicitly unretained rejected artifact remains represented by its
digest and bounded immutable observation through the retention-manifest digest in event facts. A
verified backup is incomplete until each pinned digest's exact bytes
has been copied, synced, rehashed, and listed with the database root. Cleanup cannot remove a pin
referenced by any event, proposal, evidence item, or reservation.

## 15. Projections, verification, and repair

Projection reducers are pure functions of `(projection_version, ordered canonical events,
content-addressed objects)`. They may not read wall time, environment, filesystem enumeration
order, network, random state, outbox delivery status, or existing projection rows. All SQL queries
whose order affects output use an explicit total `ORDER BY`.

`compare_projections` rebuilds into temporary/shadow tables, computes a canonical projection-state
digest, and compares it with stored projection rows and checkpoint. It never overwrites production
rows. `verify_lineage` checks canonical bytes, all hashes/links/sequences, object references,
decision/anchor bindings, reservations, receipts, outbox identities, and head equivalence from
genesis. Verification requires exact set equality—not merely existence—for every authoritative
table. The complete event history determines the exact rows of `events`, `objects`, `decisions`,
`rollback_reservations`, `requests`, `outbox`, and `artifact_pins`; it also determines the exact
singleton/current rows and values of `store_meta`, `event_head`, `lineage_heads`,
`trust_anchor_heads`, and `artifact_pin_totals`. The pure reducer determines the exact rows of
`projection_checkpoints` and `lineage_projection`. Every expected row must exist and every stored
row must be reachable from the deterministic event/receipt/root, anchor-transition,
artifact-observation, or projection-reducer graph. The only excluded table is the explicitly
operational mutable `outbox_delivery`, whose contents never enter lineage/projection equality. Any
extra, unreachable, duplicate, or missing row in any listed authoritative table is
`store.integrity_failed` and trips the `HealthLatch`.

Apart from the exact initialization-only empty-state carrier, no writer exists until a complete
verification and projection comparison from genesis reaches the observed database head and proves
equality with the external root. A matching one-event pending
extension yields only recovery-required evidence and, when independently authorized by
`read_lineage`, its bounded `RecoveryReadSession` exposing a borrowed `RecoveryReader` until
external finalization. On any
mismatch the shared `HealthLatch` trips and the writer rejects further writes with
`store.integrity_failed` or `projection.mismatch`. Restart does not clear the evidence: reopening
must repeat the complete external-root gate. Recovery creates a new database from a verified
database-plus-artifact backup or replays verified canonical events into a new file, compares roots,
and requires an explicit operator file swap and root update. There is no repair-in-place API.

## 16. Migration and compatibility

SQLite `application_id`, `user_version`, and the canonical migration/schema digest must all match.
Schema v1 is initialized only on an empty file. A future migration:

- is a reviewed, content-addressed, forward-only Rust migration;
- requires a verified database-plus-artifact backup, an external maintenance lock, and proof that
  all other database connections are closed; `BEGIN EXCLUSIVE` is not sufficient in WAL mode;
- verifies lineage and projections before and after;
- changes `user_version` and schema digest in the same transaction;
- emits no lineage event because storage layout is not a germline fact;
- never drops authoritative bytes during the M2 series;
- has no automatic downgrade or best-effort continuation.

Unknown newer versions are read-only/export-only. Older binaries must refuse them. Schema changes
require a new ADR/spec revision and shared migration fixtures.

- opened reader/writer/recovery session lifetime: configured `30,000..=300,000` ms, further bounded

## 18. Stable failure order and codes

Session/cursor operation admission is a language-level capability preflight outside the canonical
stage table. If close/expiry wins before a new session call, the call returns
`storage.interrupted` without inspecting caller bytes; if idle cursor expiry wins, resume returns
`input.cursor_invalid`. Once a call/cursor resume is admitted, the stage order below governs all
observed failures, and session invalidation at a later checkpoint maps to
`storage.interrupted` subject to mandatory pending-intent cleanup. This path-specific preflight is
frozen and cannot be reordered by an implementation.

The first failing predicate in this order wins. Predicates within a stage are evaluated in the
listed order. When one predicate applies to a collection, that predicate is evaluated across every
member in lexical canonical order before the next predicate begins; lexical order only breaks ties
between failures of the same predicate. Artifact stage 4 uses this exact predicate-major suborder
after proposal classification: exact reference-count limit; lookup I/O; unavailable or oversized existing pin; missing required
artifact; oversized required artifact; aggregate present-byte limit; digest-invalid existing pin;
digest-invalid required artifact; permanent-pin count/byte quota. The two existing-pin predicates
both map to `store.integrity_failed`; unavailable, oversized, or digest-invalid never-pinned
rejected-only artifacts instead become their closed observation statuses. This ordering permits
the aggregate bound to reject before digest streaming while still giving lookup/metadata integrity
failures precedence. Other object iteration uses the canonical event/object order.

The stage-1 authority predicates compare, in table order, the `ControlLatch`, authorization
interval, attempt-time-versus-recorded-time relation, epoch, permission,
and then principal, store slot, database, lineage, and trust-domain scope. Stage 4 checks anchor
equality or explicit transition fields in the listed order before invoking M2.1. Any remaining
M2.1 transition rejection maps to `anchor.transition_invalid`; proposal rejection maps to
`proposal.verification_failed`; both preserve the exact M2.1 code in `cause_code`. Other failures
set `cause_code:null`.

There are exactly two path-specific precedence rules outside the ordinary table walk. First,
mutation pre-BEGIN SQLite admission/lookup must succeed after stage-1 authority/input validation
and before any stage-3 completion or stage-4 predicate is evaluated; its frozen stable result still
uses stage 5 for BUSY/INTERRUPT and stage 8 for the mapped integrity/storage failures. Thus a
simultaneous later proposal, quota, anchor, or artifact predicate cannot mask the fact that its
required pre-BEGIN store read never completed. Second, finalized `initialize_lineage` retry: after exact
stage-3 stored-receipt success or `idempotency.conflict`, any absent or non-genesis-bound request
terminates with `lineage.already_initialized` and exact result `stage:3` before stage 4. This
semantic code otherwise remains at stage 6 with exact result `stage:6` for a transactional
initialization race. Therefore later quota/artifact faults cannot mask an initialization retry
mismatch, and the closed result identifies which predicate occurrence won.

The locally recomputed intent mismatch is evaluated before any root-store prepare and is therefore
the first stage-8 predicate. At a pre-finalize checkpoint, ordered control admission precedes the
exact external-intent comparison: a simultaneous pause/expiry/epoch/permission failure returns
`storage.root_publish_deferred`; only a passed control check followed by a nonmatching intent
returns `storage.root_state_conflict`. The stage-10 order above freezes that collision. Abort uses
the analogous order: failed control admission returns `storage.intent_abort_deferred`, while a
passed admission followed by foreign state returns `storage.root_state_conflict`.

For rollback at stage 7, a `failed_event_hash` that is not the current
`selected_by_event_hash`, or an absent reservation for that exact selecting event, is
`rollback.reservation_missing`. A present reservation whose target is null, whose referenced
historic selecting event is missing or invalid, or whose target bytes cannot be verified is
`rollback.target_unverified`. A non-null verified reservation that differs from the command target
genome/artifact is `rollback.target_mismatch`.

`store.quota_unavailable` means the sealed quota provider could not reserve the full configured
pre-transaction database/WAL margin for an otherwise absent operation. The independent artifact
pin bound uses `artifact.pin_quota_exceeded` on required paths as described above. After a
successful reservation, any SQLite primary `SQLITE_FULL`—whether caused by `max_page_count`, the
enforced directory quota, or an underlying allocation failure—maps only to `storage.full`; no
second `storage.quota_exceeded` interpretation exists. Exact primary/extended codes, rather than
error text, distinguish `storage.full` from `storage.io_error`.

Mutation SQLite result mapping is closed for ordinary post-BEGIN statements and COMMIT and uses
`result & 0xff` for the primary class while retaining the full extended integer only in
non-canonical diagnostics. The separate non-mutation open/read close/reset mapping in section 6
deliberately collapses every timely non-integrity error to `storage.io_error`:

| SQLite primary/extended result | Contextual mutation classification |
|---|---|
| `SQLITE_BUSY` or any `SQLITE_BUSY_*` | `storage.busy`, subject to the exact BEGIN/COMMIT retry phase |
| `SQLITE_CONSTRAINT` or any `SQLITE_CONSTRAINT_*` | `storage.constraint_failed` |
| `SQLITE_FULL` | `storage.full` |
| `SQLITE_NOMEM` | `storage.out_of_memory` |
| `SQLITE_INTERRUPT` | `storage.interrupted` |
| `SQLITE_IOERR` or any `SQLITE_IOERR_*` | `storage.io_error` |
| `SQLITE_CORRUPT`, `SQLITE_NOTADB`, `SQLITE_FORMAT`, or `SQLITE_SCHEMA`, including extended forms | before pending-intent prepare: rechecked stage-2 `store.integrity_failed`; after prepare: atomically trip `HealthLatch`, invalidate the session, retain the intent, and return `storage.intent_abort_deferred` for directly proven pre-COMMIT non-commit, `storage.commit_unknown` for unconfirmed COMMIT, or `storage.root_publish_deferred` after separately confirmed COMMIT |

Mutation-session SQLite work before `BEGIN IMMEDIATE`, including session/configuration validation
and the stage-3 idempotency lookup, uses the same primary-to-stable-code rows but has no transaction
or pending intent to clean up. `SQLITE_BUSY*` is stage-5 `storage.busy`; a deadline-driven
`SQLITE_INTERRUPT` is stage-5 `storage.interrupted`; and CONSTRAINT/FULL/IOERR/NOMEM/unsupported
results use their stage-8 rows above. An integrity primary anywhere before pending-intent prepare,
including stage-2 store/session/schema/PRAGMA validation or the later idempotency lookup,
atomically trips the `HealthLatch` as rechecked stage-2 `store.integrity_failed`. These
storage outcomes supersede a tentative idempotency result that could not be completely read and
verified; a completely verified stored receipt or conflict wins only after all SQLite calls
required for that lookup have succeeded. No pre-BEGIN error may be
reclassified as `store.open_failed`, publish an intent, reserve mutation quota, or enter the
post-BEGIN cleanup/autocommit matrix.

Success-like SQLite statuses are also call-specific and closed over the private adapter enum
`SqliteResultCallKind`:

| Call kind | Allowed success statuses |
|---|---|
| `ConnectionControl` (open/configuration), `Prepare`, or `TransactionControl` (fixed `BEGIN IMMEDIATE`, `COMMIT`, `ROLLBACK`) | `SQLITE_OK` only |
| `BindOrStatementControl` (`sqlite3_bind_*` and `sqlite3_clear_bindings`) | `SQLITE_OK` only; every non-OK status uses the applicable pre- or post-BEGIN failure mapping |
| `ReadStep` (fixed read-only `sqlite3_step`) | zero or more `SQLITE_ROW` values with contract-checked shape/cardinality, then exactly one `SQLITE_DONE` |
| `MutationStep` (fixed mutating `sqlite3_step` without `RETURNING`) | exactly one `SQLITE_DONE`; `sqlite3_changes64()` must satisfy the operation's exact row-count postcondition |
| `BackupStep` | `SQLITE_OK` while pages remain, then exactly one `SQLITE_DONE`; `SQLITE_BUSY`/`SQLITE_LOCKED` are bounded maintenance failures/retries, never success |

| `WalCheckpoint` | `SQLITE_OK` only plus mode-specific checked log/checkpoint counters; `SQLITE_BUSY`/`SQLITE_LOCKED` are bounded maintenance failures/retries, never success |

| `CleanupResetOrFinalize` | `SQLITE_OK` or the already captured statement failure code; the latter preserves the original mapped failure and is never reinterpreted as cleanup success |

`sqlite3_backup_init()` is wrapped separately as `BackupInit`: a non-null owned handle is success;
null is failure and the **destination connection's** exact extended result enters the maintenance
failure rule. Maintenance emits no canonical protocol result: `SQLITE_BUSY`/`SQLITE_LOCKED` from a
backup step or checkpoint may be retried at most 8 times including the first call and only within
the one aggregate maintenance deadline; exhaustion, any other mapped failure, a null backup-init,
or a non-OK backup-finish/close aborts publication, retains the exact numeric code only in
non-authoritative diagnostics, and runs the bounded maintenance cleanup. `BackupFinish` preserves
the last backup-step failure when SQLite specifies it; it cannot overwrite that failure with a
later status. No failed maintenance path mutates lineage/root authority or publishes a partial
destination.
Void/value-returning calls such as interrupt/progress-handler installation, `get_autocommit`,
`changes64`, and backup/checkpoint counters use distinct typed adapter methods and cannot be passed
through `SqliteResultCallKind`. Every SQLite API used by M2.2 must be named by one of these sealed
adapter methods; a new API/call kind requires a reviewed spec revision and fixture. `SQLITE_OK`,
`SQLITE_ROW`, or `SQLITE_DONE` in any other result-call context is a context-invalid result,
maps to `storage.io_error`, and enters the same cleanup rules; it cannot be reinterpreted as
success. Cleanup-only finalize/reset APIs may surface the statement's retained failure code, but
that cannot replace the original mapped result or publish evidence.

This mutation mapping applies identically to ordinary post-BEGIN statements and COMMIT. It never bypasses
the cleanup/autocommit/receipt matrix: a verified receipt confirms SQLite commit and proceeds to
root finalization, unprovable absence is `storage.commit_unknown`, and deferred/unknown intent
cleanup supersedes the mapped ordinary code. No SQLite error string participates in precedence.

`retryable` is true only for `artifact.io_error`, `storage.busy`, `storage.interrupted`,
`storage.intent_publish_unknown`, `storage.intent_abort_deferred`, `storage.commit_unknown`,
`storage.root_state_conflict`, `storage.root_publish_deferred`, and
`storage.root_publish_unknown`. `store.integrity_failed`, `storage.constraint_failed`, `storage.full`,
`storage.out_of_memory`, and `storage.io_error` are not automatically retryable. An event/head CAS mismatch requires a new operator-approved
command, not an automatic retry, and therefore reports false; external-root CAS outcomes follow
their separate closed matrix in section 6. Unknown SQLite extended codes map to `storage.io_error` and retain the numeric
SQLite code only in non-canonical diagnostics.

## 19. Crash and fault model

Fault injection must stop the process or force an error before and after every step in section 12,
including every row insert, both CAS updates, request insertion, pre-commit check, commit call, and
post-commit receipt publication.

After reopening:

- the database contains either none or all of one command's authoritative rows;
- no event exists without its object/decision/reservation/outbox/receipt dependencies;
- no head points to a missing or uncommitted event;
- the hash chain and projection comparison pass;
- a retry returns the original receipt or safely performs the one absent transaction;
- no downstream/application effect is emitted for an uncommitted outbox row;
- power-loss durability claims are made only for WAL + `synchronous=FULL` on a filesystem and
  storage stack that honors SQLite's locking and sync assumptions.

Database/WAL truncation, bit flips, main-file-only copy, stale replacement, disk full, busy writer,
I/O failure, process kill, and post-commit response loss all require fixtures or integration tests.
The fault harness must also inject VFS `xWrite`, `xSync`, `xTruncate`, locking/shared-memory, and
power-cut failures around WAL append, commit mark, checkpoint, pending-intent prepare, and root
finalization.

## 20. Observability

After confirmed SQLite commit and durable external-root finalization, the writer may emit a
vendor-neutral event containing operation kind, request ID, command digest, event hash/sequence,
lineage ID/generation, decision status, latency, busy retries, database size, WAL size, and result
code. It must not contain private keys, raw
evidence details, candidate metadata, artifact contents, or authority grants.

Telemetry is derived and non-authoritative. Export failure is recorded locally and never changes
the receipt. Trace IDs are not event identity and cannot be used for idempotency.

    genesis sentinel/conditional insert, rejection on initialized/unknown lineage, compact outbox
    maximal-schema-valid canonical bytes and proof they fit the 4,096-byte defensive cap, private
    bounded-encoder 4,096/4,097 synthetic-byte unit vectors, immutable-row mutation denial,
    one-lineage-per-database, exact public sealed
    carrier/result matrices, and every stable-code precedence collision;
17. Linux/macOS/Windows CI plus a local-filesystem clean-clone run;
18. a second three-role automated review with no P0/P1/P2 before any writer code is enabled.

The implementation Definition of Done additionally requires Rust-only production writes, the
exact reviewed SQLite 3.53.4 source ID, full fault injection, default-disabled integration, clean
reproduction, and a later human security review before production use.

## 22. Rollback/removal of M2.2

Until release, remove the disabled writer module and its unopened test database while retaining
the normative spec, schemas, fixtures, and evidence. Never downgrade or rewrite a database that
has committed M2.2 events. Export verified canonical events and restore the prior non-authorizing
M2.1 runtime. External deployment remains absent, so removing the writer cannot require code
rollback in a phenotype.
